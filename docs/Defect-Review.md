## 一、前端应用设计缺陷与后果

### 1.1 乐观锁 UX 中的「静默覆盖」风险

**漏洞**：用户在编辑器里改第三章，同时 AI 也在写第三章。如果前端保存时不携带
`base_version`，后保存的人会静默覆盖先保存的人的稿子——**先写的内容彻底丢失**，
且用户毫不知情。

**后果**：用户辛苦手写的正文被 AI 生成的内容无提示覆盖，数据不可恢复。

**已落地对策**：
- 前端 `PUT /chapters/{cid}/content` **必携 `base_version`**（DTO 上 `Field(ge=1)` 必填）；
- 版本不符时返回 409/40901 且 `data` 回传最新内容 + `last_writer`（manual/agent）；
- 前端弹 `ConflictBanner` 让用户选「看差异合并」或「以我的为准」——**绝不静默覆盖**。

### 1.2 回退编辑栈的内存泄漏风险

**漏洞**：编辑器如果无限记录撤销快照，几分钟打字就能积累几百条快照，
不仅内存膨胀，而且真正想回滚时在海量无意义版本中找不到目标。

**后果**：浏览器内存暴涨、编辑器卡顿、版本列表不可用。

**已落地对策**：
- 回退编辑栈上限 **5 条**（`undoStack`）；
- 800ms 防抖把连续输入并成一个撤销点；
- 换章与 reset 时清空栈。

### 1.3 SSE 断线后的「幽灵消息」问题

**漏洞**：SSE 流式传输中，如果断线重连后不清空本地流式缓冲，
同一条 AI 回复可能被显示两次——一次来自旧缓冲，一次来自重拉消息树。

**后果**：用户看到重复消息，困惑且无法判断哪条是真实回复。

**已落地对策**：
- 重拉消息树时**清空流式缓冲**；
- 收到 `error(41001)`（缓冲丢失）时回落重拉全量消息。

### 1.4 运行/暂停中显示中间消息

**漏洞**：Agent 处理过程中会产生大量思考/工具调用的中间消息。
如果在运行中实时展示这些消息，用户会看到大量混乱的中间过程，
而真正的结论被淹没。

**后果**：用户体验混乱，无法区分「AI 正在思考」和「AI 给出了结论」。

**已落地对策**：
- `collapseTurns(list, running || runPaused)` 隐藏本轮非用户消息；
- 每个用户轮只留最后一条非空 AI 消息，中间过程走折叠区；
- 等 Agent 整体处理完（run.end 非 paused）才呈现结论。

### 1.5 AI 气泡误用正文排版

**漏洞**：如果把小说正文的排版样式（1.9 行高 + 32/120px 内边距 + 2em 首行缩进）
用在 Agent 对话气泡上，会出现大片留白和异常排版。

**后果**：Agent 面板消息气泡排版异常，用户体验差。

**已落地对策**：
- AI 气泡只挂 `.msg-prose`（不复用 `.novel-prose`）；
- 渲染前 `trimTrailing()` 去掉模型尾随换行（markdown-it `breaks:true` 会把尾随换行变成额外 `<br>`）。

### 1.6 SPA 回落的路径穿越

**漏洞**：前端 SPA history 回落把非 API 路径返回 `index.html`。
如果 `full_path` 未经净化直接拼接到文件系统路径，`/etc/passwd` 或 `..%2f` 解码后的
`../` 都可能逃出 `dist` 目录。

**后果**：**信息泄露**——攻击者可读取 `.env` 中的模型密钥等敏感文件。

**已落地对策**：
- `_mount_frontend()` 中 `candidate.resolve()` 后严格检查 `is_relative_to(dist_resolved)`；
- 非文件或非 dist 内路径一律返回 `index.html`。

### 1.7 浏览器定位的权限与协议限制

**漏洞**：浏览器 Geolocation API 需要 HTTPS 或 localhost，且用户可拒绝授权。
如果前端不做回落处理，定位失败后天气组件会完全不可用。

**后果**：用户拒绝定位或 HTTP 环境下天气组件报错或白屏。

**已落地对策**：
- 拒绝/失败/超时 → 回落 `user_settings.city`；
- 再失败只显示宠物与占位天气；
- **坐标不入库、不写审计**（隐私保护）。

### 1.8 模型下拉的记忆失效

**漏洞**：用户选了一个非默认模型发消息，前端记忆到 `localStorage`。
如果后续该模型被删除，前端仍尝试使用已不存在的模型引用。

**后果**：发送消息时模型解析失败，用户收到不明确的错误提示。

**已落地对策**：
- 记忆上次所选模型到 `localStorage`，**需仍在可用列表内**才使用；
- 失效则回落默认模型。

## 二、后端应用设计缺陷与后果

### 2.1 文件与数据库双源不一致

**漏洞**：正文既存在文件中又存在数据库中，如果写入只更新了其中一方，
两者就会产生不一致。用户看到的版本和实际磁盘上的版本可能不同。

**后果**：数据错乱——导出时拿到旧版本，检索命中已删除内容，字数统计不准。

**已落地对策**：
- **文件为内容事实源，DB 为登记与索引**——不一致时以文件为准；
- 派生索引写失败**不阻断正文保存**，只标 `project_index.dirty=1` 待重建；
- `writer rebuild-index` / `POST /novels/{id}/index/rebuild` 全量重建。

### 2.2 修订快照爆炸

**漏洞**：如果自动保存每次都产生修订快照，用户打字几分钟就能刷出几百条无意义的
版本记录，真正想回滚时反而找不到目标。

**后果**：数据库膨胀、快照列表不可用、用户无法有效回滚。

**已落地对策**：
- **自动保存不产生快照**（`is_autosave`）；
- 快照只在「手动保存 / Agent 写入前 / 章节定稿」三个时刻产生；
- `_prune_revisions` 保留最近 20 条。

### 2.3 卷章顺序双源漂移

**漏洞**：如果卷章顺序有两个来源（大纲小节先后 + `sort_order` 字段），
两者迟早打架——大纲改一个字，卷章树顺序就变了，还容易产生「大纲有、树里没有」
的漂移。

**后果**：目录树顺序混乱、用户无法理解为什么改大纲会影响卷章排列。

**已落地对策**：
- **大纲降级为参考资料**，不再回填 `sort_order`；
- 顺序只有「插入」一个写入口（插入到第 k 位则该位及其后顺延 +1、删除后重新连续编号）；
- 前端无拖拽/上移下移，后端无 `reorder`/`move`（测试断言路由不存在）；
- `assert_no_manual_reorder()` 守卫函数 + 测试断言。

### 2.4 误删章节不可恢复

**漏洞**：如果删除操作直接 `unlink` 文件，用户的误删就不可恢复。

**后果**：用户辛苦写的内容永久丢失。

**已落地对策**：
- **回收站**：删除落盘**之前**先归档到 `data/recycle/{project_id}/`（最多 20 本）；
- 整本删除登记 `novel_deleted=true` + `trash_dir`；
- 恢复任一章时若整本已删则先把工作区搬回（连项目与大纲一起复原）；
- Agent 的 delete 同样走回收站（`SafeDeleteMiddleware`）。

### 2.5 小说重命名与大纲文件名耦合

**漏洞**：大纲文件名格式为 `{title}-大纲.md`，小说重命名时如果只改了 DB 中的标题
而忘了改文件名，大纲文件就找不到了。

**后果**：大纲丢失——用户打开大纲页面显示空白。

**已落地对策**：
- 重命名是**事务**：同步重命名 outline 文件 + 更新 `novel.yaml` + 更新 DB；
- 任一步失败整体回滚；
- `outline_file` 为唯一寻址依据。

### 2.6 并发写入同一 run 被 resolve 与进行中的任务冲突

**漏洞**：用户点击审批「批准」的同时，Agent 正在执行另一个操作。
如果两者并发写同一个 LangGraph thread，状态就会损坏。

**后果**：Agent 运行状态损坏，中断永远无法恢复，run 永久挂起。

**已落地对策**：
- `RunManager._spawn` 用 **per-run `asyncio.Lock`** 串行化。

### 2.7 FTS5 不可用时的静默失败

**漏洞**：SQLite FTS5 在某些环境下不可用（未编译 fts5 扩展）。
如果不做探测和降级，检索功能会一直报错。

**后果**：用户搜索永远返回错误。

**已落地对策**：
- **两步探测**：先 `SELECT fts5(NULL)` 再建临时表验证 `unicode61` + `bm25()`；
- 任一步失败即**永久降级** `LIKE`（进程内缓存）；
- 降级后接口签名与返回结构不变（只多 `data.degraded=true`）。

### 2.8 密钥泄露风险

**漏洞**：如果 API Key 明文存在数据库中，数据库文件被拷贝或被攻击者访问时
密钥就泄露了。

**后果**：攻击者可使用用户的 LLM API 额度产生费用。

**已落地对策**：
- API Key **只存系统级环境变量**（Windows 注册表 HKCU / 类 Unix `~/.ai-writer-pro/env.json` 0600）；
- DB 仅存 `api_key_env`（变量名引用，不存值）；
- UI 展示掩码 `sk-****abcd`；
- 日志 processor 对 `key`/`token`/`secret` 字段自动掩码。

### 2.9 stdio MCP 的「受限任意命令执行」风险

**漏洞**：如果允许用户注册任意 stdio 命令作为 MCP 服务，
等价于给了用户（或 Agent）在本机执行任意命令的能力。

**后果**：远程代码执行（RCE）漏洞。

**已落地对策**：
- 可执行文件**白名单**（`npx`/`uvx`/`python`，拒绝任意路径命令）；
- 用户**二次显式确认**（展示完整命令，写 `confirmed_at`）；
- **命令全文落审计**。

### 2.10 回收站 URL 路径穿越

**漏洞**：回收站的 URL 含 `novel_id` / `chapter_id` 参数。
如果不做校验，攻击者可构造 `../../etc/passwd` 等路径穿越参数。

**后果**：越权访问非回收站数据。

**已落地对策**：
- 回收站不经 WorkspaceGuard，故 **ID 白名单校验**（必须是合法的 uuid 格式）；
- 测试断言路径穿越被拒。

## 三、Agent 核心设计缺陷与后果

### 3.1 权限顺序写错 → 全线放行

**漏洞**：deepagents `permissions` 的判定机制是**首条匹配生效、无匹配默认 `allow`**。
如果兜底的 `deny /**` 排在了前面，后面所有规则全部失效——等于**全线放行**。
反过来，如果漏了兜底 deny，也是全线放行。

**后果**：**安全漏洞**——Agent 可以读写任意路径，包括系统文件、其他项目、密钥文件等。

**已落地对策**：
- 8 条规则以 **`PERMISSION_RULES` 常量数组**集中定义；
- 兜底 `deny /**` **必须最后**；
- **编码成常量 + 配回归测试**：`test_permissions.py` 逐行断言常量数组与设计表一致；
- **第二道防线**：`WorkspaceGuardMiddleware` 兜底。

### 3.2 Agent 能改技能文件 → 自我改造

**漏洞**：如果 Agent 可以写 `/skills/**` 路径，它就能给自己写新指令——
创建一个 SKILL.md 告诉自己在某些情况下执行某些操作。

**后果**：Agent 行为不可预测，安全边界被彻底突破。

**已落地对策**：
- 权限规则 ⑤：`/skills/**` **禁写**（技能由服务层维护）；
- WorkspaceGuard 第二道防线同样拒绝技能区写入。

### 3.3 权限不覆盖自定义工具 → 越权盲区

**漏洞**：`permissions` 只作用于 deepagents 内置文件工具（ls/read_file/write_file 等）。
自定义工具（如 `web_search`）和 MCP 工具不在其覆盖范围。
如果自定义工具中有涉及文件操作的，权限规则就对它们无效。

**后果**：Agent 可通过自定义工具绕过权限规则。

**已落地对策**：
- **收窄越权面**：自定义工具只有不碰路径的三个（`web_search` / `outline_grep` / `ask_user`）+ 6 个结构工具（经 services 层校验）；
- `WorkspaceGuardMiddleware` 覆盖所有工具（第二道防线）。

### 3.4 `interrupt_on` 只能做工具级开关 → 误审批或漏审批

**漏洞**：`interrupt_on={"delete": True}` 会对所有 delete 操作弹审批卡，
但 `write_file` 覆盖一个空文件没事，覆盖一个 3000 字的定稿章节就是灾难。
工具级开关无法区分这两种情况。

**后果**：要么审批太多（空文件也要批），要么审批太少（覆盖定稿不弹卡）。

**已落地对策**：
- `INTERRUPT_ON = {}`（置空）；
- 自研 `WriteApprovalMiddleware` 做**参数级**判定：
  - `write_file` 目标是已存在的非空章节且内容不同 → 整章覆盖审批；
  - `edit_file` 超 800 字符 → 大范围改写审批；
  - `delete` 任何项目内文件 → 不可逆审批；
- ★必须装在**最外层**（`GraphInterrupt` 不能被吞）。

### 3.5 GraphInterrupt 被外层 try/except 吞掉

**漏洞**：`WriteApprovalMiddleware` 调用 `interrupt()` 暂停 run 时抛出 `GraphInterrupt`。
如果外层中间件有 try/except 捕获了它，就变成了错误 ToolMessage 返回给模型——
审批永远无法暂停 run。

**后果**：审批机制完全失效，高危操作（覆盖定稿、删除章节）不会弹卡确认。

**已落地对策**：
- `WriteApprovalMiddleware` 装配在**最外层**；
- `WorkspaceGuardMiddleware` 中工具 handler 抛出的 `GraphBubbleUp`（interrupt 暂停）**必须原样上抛**，不得被错误兜底吞成 ToolMessage。

### 3.6 模型在同一个坑里反复撞墙 → token 烧光

**漏洞**：模型对同一个工具调用参数反复重试（如反复读同一个不存在的文件），
每次都消耗 token，但永远无法成功。

**后果**：单次 run 的 token 消耗失控（实测案例：718K 输入 token），用户费用暴涨。

**已落地对策**：
- **错误指纹记忆**（WorkspaceGuard）：对 `(tool_name, args_hash, error_fingerprint)` 计数，
  2 次注入告警 ToolMessage，3 次直接阻断该调用路径；
- **浪费型循环分级熔断**（WastefulLoopGuard）：
  - SOFT=3 次 → 注入纠正提醒；
  - HARD=5 次 → 注入强制换方向指令 + 工具层硬阻断。

### 3.7 工具消息配对错位 → 模型看到混乱上下文

**漏洞**：一次 AIMessage 带多个并行 tool_calls 时，state 里的 ToolMessage 列表偶发错位——
某条结果丢失、另一条结果重复成对。

**后果**：模型看到「重复循环的异常内容」并反复重读附件，token 暴涨。

**已落地对策**：
- `PairingRepairMiddleware` 在每次模型调用前校验配对：
  `AIMessage.tool_calls` 的 id 序列必须与其后连续 ToolMessage 的 `tool_call_id` 一一对应；
  错位时按位置**原地修复**。

### 3.8 上下文窗口配置中途变更 → 压缩阈值不同步

**漏洞**：压缩中间件的触发阈值在装配 graph 时按当时的 Context Length 固定。
如果用户中途在「AI 设置」把窗口改小，正在跑的 run 仍按旧阈值判定。

**后果**：可能出现「比例已超 20% 剩余却不压缩」的窗口期，最终触发 provider 报错。

**已落地对策**：
- `ContextWindowSyncMiddleware` 在每次模型调用前实时读取模型行的 `max_context`，
  重算触发点并**原地改写**压缩中间件的阈值子句。

### 3.9 设定 Context Length > 模型真实窗口 → provider 报错

**漏洞**：用户在 AI 设置中声明的 Context Length 可能大于模型真实窗口。
此时压缩中间件不会介入（因为声明窗口还没到阈值），但 provider 会直接报上下文超限错误。

**后果**：run 失败，用户收到不明确的错误信息。

**已落地对策**：
- `ContextOverflowGuardMiddleware` 捕获 provider 的超限错误（含 DashScope 等 deepagents
  未识别的文案），把旧消息摘要后重试。

### 3.10 Resume 值的竞态条件（并行工具调用）

**漏洞**：模型并行发多个高危调用时，每个都会产生审批中断。
用户批准其中一张卡时，如果 resume 值投递错了目标（投给了另一个高危调用），
那个操作就会**未经批准就被执行**——比如删了章节。

**后果**：**安全漏洞**——未经人工批准的删除/覆盖操作被执行。

**已落地对策**：
- **中断挂起一律按 id 定向**（`lifecycle.resume_input_for` 构造映射）；
- 已决但值未送达的兄弟中断 → 用落库 response 一并送达；
- **失败关闭（fail-closed）**：本次决定对不上任何挂起中断时，若库里还有另一张未决卡
  正对应某个挂起中断，**绝不投递**——保持挂起，重放时再次 `interrupt()`。

### 3.11 Checkpointer 非单例 → 中断态丢失

**漏洞**：aiosqlite 连接须长生命周期持有。如果每个 run 重开 checkpointer，
之前的中断态就丢了。

**后果**：用户批准审批卡后 Agent 无法恢复运行，run 永久挂起。

**已落地对策**：
- `AsyncSqliteSaver` **进程内单例**（`asyncio.Lock` + 双检）；
- `DATA_ROOT` 变化时自动重开（否则测试会串库）。

### 3.12 消息树双轨不一致

**漏洞**：消息既要给前端渲染/审计（业务库），又要给 LangGraph 恢复运行（checkpoint）。
graph state 里的消息 id 由 LangGraph 生成，与业务库 uuid **无对应关系**。

**后果**：前端显示的消息与 Agent 恢复时看到的消息不一致，导致对话错乱。

**已落地对策**：
- **索引基线增量同步**（不按 id 匹配）：利用 state 的 messages 是追加式的性质，
  只记「已同步到的下标」，每次 sync 只处理新增部分；
- 未完成消息不落库，中断时 `force=True` 强制落库。

### 3.13 子代理栈缺少安全中间件 → 静默删除/覆盖

**漏洞**：deepagents 只按中间件 name 把主栈中间件继承给子代理的基座槽位，
自建中间件不在其中。如果子代理栈上没有 WriteApproval / SafeDelete / ContentLock 等，
writer 子代理就能静默删章、覆盖正文。

**后果**：**安全漏洞**——子代理绕过所有安全防护直接操作文件。

**已落地对策**：
- 子代理栈必须**与主栈同构**地挂载安全中间件（WriteApproval / WorkspaceGuard /
  ContentLock / FileChangeNotify / SafeDelete 等）；
- `SubagentContextScrubMiddleware` 在子代理结束时清空中间上下文。

### 3.14 Agent 的 delete 是永久物理删除 → 不走回收站

**漏洞**：deepagents 的 `FilesystemBackend.delete` 是 `unlink()` / `rmtree()`——
直接物理删除，不进回收站。

**后果**：Agent 误删（或附件里的提示注入诱导删除）损失不可逆。

**已落地对策**：
- `SafeDeleteMiddleware` 拦截 delete 工具调用：
  - 章节文件 → 调 `volumes.delete_chapter`，走回收站归档；
  - 其它路径 → 搬进 `data/trash/agent-deleted/`；
  - 服务层失败 → 返回错误 ToolMessage（**fail-closed**，绝不退化成物理删除）。

### 3.15 流程 S3 反复重生成不收敛 → 死循环

**漏洞**：S3 后检发现生成的正文不匹配大纲简介时自动重生成，
但如果模型始终无法生成匹配内容，就会无限循环。

**后果**：run 永远不结束，token 无限消耗。

**已落地对策**：
- `POSTCHECK_MAX_RETRY=2` 上限；
- 每次重生前快照（可回滚）；
- 仍不匹配发咨询卡片兜底（认可现状/手动修改/补充指示）。

### 3.16 上下文膨胀 → 长篇写作成本失控

**漏洞**：长篇小说逐章累积，若把历史章节全塞进上下文会爆窗口且成本失控。

**后果**：单次 run 的 token 费用暴涨（实测案例：718K 输入 token），用户不堪重负。

**已落地对策**（多层组合）：
1. 前情提要替代原文（摘要 ≤600 字）；
2. token 预算检查 + `context.compact` 事件；
3. summarization 驱逐卸载；
4. 子代理上下文隔离（`mode=isolated`）；
5. 调用次数双限（软上限 60 + 硬上限 60）；
6. checkpoint 增量存储（`DeltaChannel(snapshot_frequency=50)`）；
7. 浪费型循环分级熔断；
8. 显式前缀缓存断点（跨 run/run 内复用折扣）。

### 3.17 流程功能被劈成两半 → 维护困难

**漏洞**：状态机在 `writing_steps/`、运行编排在 `loop/runner.py`，
读流程必须跨文件跳转。

**后果**：代码可读性差，改流程容易改错位置，维护成本高。

**已落地对策**：
- `_execute_chapter_workflow` 及辅助函数整体迁入 `writing_steps/runner.py`，
  与 `orchestrator.py` 同住；
- `loop/runner.py` 从 1420 行缩减到 375 行。

### 3.18 「幽灵卡」竞态——审批卡已建而中断未落 checkpoint

**漏洞**：某任务的 `interrupt()` 被取消时，审批卡已建（落 `agent_interrupts` 行）
但中断未落 checkpoint。用户批准这张「幽灵卡」时，如果退回标量 resume，
该批准会被**另一个**高危写入当成自己的答复直接执行。

**后果**：**安全漏洞**——未经批准的高危操作（如删除章节）被静默执行。

**已落地对策**：
- **失败关闭**：本次决定对不上任何挂起中断时，若库里还有另一张未决卡正对应某个
  挂起中断，**绝不投递**——返回占位键映射，langgraph 忽略之，对应任务重放时再次
  `interrupt()` 挂起，用户仍会看到那张真正待批的卡。

## 四、已落地的防护与对策汇总

### 4.1 「把约束编码成常量 + 配回归测试」

本项目最有价值的质量手法——设计约束不写在文档里靠人工自觉，
而是**编码成常量并配回归测试**：

| 约束                    | 落地方式                                                                                                              |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 权限规则顺序即语义      | `PERMISSION_RULES` 常量 + 顺序回归测试                                                                              |
| 错误码规范              | `ErrorCode` 常量 + `CODE_TO_HTTP` / `CODE_TO_MESSAGE` **双映射表**                                        |
| 路径与编码统一          | `core/paths.py` 集中解析，全部 `pathlib` + 显式 `encoding="utf-8"`                                                |
| ID 稳定、顺序单一写入口 | 顺序由**插入**维护，**无 reorder / move 接口**（测试断言路由不存在）+ `assert_no_manual_reorder()` 守卫 |
| 技能物化合规            | 测试断言 frontmatter `name`==目录名、description ≤1024、≤10MB                                                       |
| 回收站不丢数据          | 归档 + 20 本上限淘汰；测试断言恢复可重建级联删除的卷                                                                 |
| Resume 失败关闭         | 测试断言「幽灵卡」批准时另一张未决卡保持挂起                                                                         |

### 4.2 安全防护层次图

```
用户操作
  │
  ├─ 前端层：乐观锁（base_version）+ ConflictBanner + 未保存拦截
  │
  ├─ API 层：参数校验（Pydantic DTO）+ 统一错误码
  │
  ├─ 服务层：WorkspaceGuard（唯一文件写入口）+ 乐观锁 + 修订快照 + 回收站
  │
  ├─ Agent 权限层：8 条有序 permissions（第一道防线）
  │
  ├─ Agent 中间件层（17 层）：
  │   WriteApproval（参数级 HITL）
  │   WorkspaceGuard（第二道路径防线 + 错误指纹阻断）
  │   SafeDelete（可恢复删除）
  │   ReadScopeGuard（读取授权守卫）
  │   ContentLock（AI 编辑锁）
  │   WastefulLoopGuard（浪费熔断）
  │   ModelCallBudget（调用预算）
  │
  └─ 框架层：deepagents FilesystemMiddleware + checkpointer + interrupt
```

### 4.3 测试覆盖策略

23 个测试文件，核心手法：
- **httpx `ASGITransport` 直连** FastAPI 应用（不起真实服务器）；
- **假模型驱动**（`fake_model.py`）：可编排的 ChatModel 替身，**不触网、不打真实 LLM**；
- 每测试独立 `DATA_ROOT` + `reset_engine()` + `reset_checkpointer()` 做隔离。
