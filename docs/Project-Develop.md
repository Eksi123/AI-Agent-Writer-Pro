## 一、项目定位

**AI Agent Writer Pro** 是一个大纲驱动的 AI 小说写作工作台，**单用户本地应用**
（无登录鉴权、无后台管理端、审计日志只读）。

它本质上是一个小说编辑器，支持两种写作模式：

1. **手动撰写** —— 人写正文，走常规 CRUD + 乐观锁 + 修订快照；
2. **AI 生成** —— Agent 写正文，但**必须以大纲章简介为前提**（四阶段固定流程 S0→S3 硬编排）。

项目要同时回答两个命题：

| 命题                                        | 答案落点                                                                                                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **怎么设计 AI Agent？**               | 不自研框架，用 deepagents（LangGraph 之上）做**写作领域化封装**：LLM 接入与韧性、Agent-Loop、工具/技能/子代理/MCP、消息树、沙箱半隔离、流程编排、可观测 |
| **怎么在 Agent 上开发 Writer 应用？** | C/S 分离：Vue 3 三栏工作台 + FastAPI 后端；**文件为内容事实源，DB 为登记与派生索引**；写作业务下沉为 REST 接口，Agent 只用文件工具碰内容                |

### 设计铁律

1. 不自研 Agent 框架，只做写作领域化封装；
2. C/S 分离（REST 取数 + SSE 流式 + REST 控制）；
3. **文件为内容事实源，DB 为登记与索引**，不一致时以文件为准（可 `rebuild-index` 重建）；
4. 单用户 + 项目级隔离（Agent 跨项目**可读不可写**）；
5. Langfuse 可观测，未配置自动降级；
6. **显式命名**（禁止「未命名小说」「第 1 卷」等默认名，违规 `42201`）；
7. UI 默认中文，文案集中管理；
8. permissions **首条匹配生效**、兜底 `deny /**` 必须最后；
9. **ID 稳定、顺序由「插入」维护**（起大纲降级为参考资料，不再回填 `sort_order`；
   卷章顺序由 `services/volumes.py` 维护：插入到第 k 位则该位及其后各项 +1、删后重新连续编号；
   仍**无 reorder / move 接口**，插入是唯一的位置编辑入口）；
10. 时间戳一律 UTC ISO-8601 应用层写入（不用 SQLite 触发器 / `CURRENT_TIMESTAMP`）；
11. 文件读写一律 `pathlib` + 显式 `encoding="utf-8"`（Windows 兼容）。

其中 8、9、6、11 四条都被**编码成常量 + 配套回归测试**，而非只写在文档里靠人工自觉
（见 [九、测试与质量保障](#九测试与质量保障)）。

## 二、项目大纲层次

### 2.1 功能层次（自顶向下）

```
AI Agent Writer Pro
│
├─ 写作业务层（人工撰写，不经 Agent）
│   ├─ 项目管理：小说 CRUD / 软删除 / 复制 / 导出
│   ├─ 回收站：被删章节归档（最多 20 本）/ 卷章浏览 / 回收 / 彻底删除
│   ├─ 卷章管理：卷章 CRUD / 短 ID 恒定 / 顺序由「插入」维护（无 reorder）
│   ├─ 正文编辑：乐观锁 / 修订快照 / 自动保存 / 回退编辑（≤5 次）/ 选区 AI 改写
│   ├─ 大纲维护：单文件大纲 / 严格解析 / 格式校验（★大纲是参考资料，不回填顺序）
│   ├─ 阅读模式：目录 / 翻页 / 进度记忆 / 夜间模式
│   └─ 检索：FTS5 二元切分 / LIKE 降级
│
├─ AI Agent 层（AI 生成与对话）
│   ├─ LLM 接入：多厂商 / 四层参数 / 降级链 / 密钥安全
│   ├─ Agent-Loop：主循环装配 / 流式 / 中断恢复 / 取消 / 收尾
│   ├─ Tools：文件工具（受 permissions 约束）/ web_search / MCP
│   ├─ Sub-agents：5 个内置子代理（4 写作 + recaller 记忆召回）+ general-purpose
│   ├─ Skills：用户自建（虚拟路径挂载 /skills/user/）
│   ├─ Chapter Workflow：S0→S3 四阶段固定流程 + 咨询卡片
│   ├─ Memory：消息树 / 分支 / 双轨持久化
│   ├─ Knowledge：前情提要 / 章节摘要 / 大纲解析
│   ├─ Sandbox：CompositeBackend 路由 + 8 条有序权限
│   ├─ Prompts：Jinja2 模板（独立版本化）
│   └─ Tracing：Langfuse v5（未配 Key 自动降级）
│
└─ 平台支撑层
    ├─ 统一响应包装 / 错误码 / 全局异常处理
    ├─ 审计日志（SQLite + JSONL 双写，只读 API）
    ├─ 通用设置（user_settings 单行表）
    ├─ 动态组件（宠物两态 / 城市定位 / 天气）
    └─ 数据一致性（派生索引 + dirty 标记 + 全量重建）
```

### 2.3 依赖方向与边界

```
                    ┌──────────────────────────────────────┐
   浏览器（Vue 3）  │  三栏布局：左侧项目栏 / 中间阅读编辑 / 右侧 Agent 面板
                    └───────────────┬──────────────────────┘
                        REST /api/v1 │ SSE /agent/runs/{id}/stream
                    ┌───────────────▼──────────────────────┐
                    │ api/        路由层（薄，只做协议转换）│
                    └───────────────┬──────────────────────┘
                                    │ 取数一律经 services
                    ┌───────────────▼──────────────────────┐
                    │ services/   业务编排层                │
                    └──────┬────────────────────────┬──────┘
                           │                        │ agent 可用 services
              ┌────────────▼───────────┐            │ （单向，无环）
              │ core/ + db/ + schemas/ │   ┌────────▼────────┐
              │ 基础设施 / ORM / DTO   │◀──┤ agent/          │
              └────────────────────────┘   │ ★AI Agent 全部  │
              │   逻辑（7 目录）│
                                           └─────────────────┘
```

**边界约定**（这是本项目最重要的组织特征，任何改动都应保持）：

| 方向                    | 允许性                        | 说明                                                                                                                                       |
| ----------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `api/ → services/`   | ✅ 唯一取数路径               | 15 个 api 模块全部经 services                                                                                                              |
| `api/ → agent/`      | ✅ **仅运行入口**       | 只 `api/agent.py` 持有 `run_manager` + `sse_bus`（起 run / 订阅流）；`api/chapters.py` 持 `rewrite`（服务层直连 LLM 的选区改写） |
| `agent/ → services/` | ✅ 允许方向                   | workflows / knowledge / loop / more/mcp 用业务服务（大纲解析、文件写入、索引重建）                                                         |
| `services/ → agent/` | ⚠️ **两处文档化例外** | ① `services/agent.py` → `agent.tracing.messages`（消息树读写）② `services/search.py` → `agent.loop.knowledge`（章节摘要生成）  |
| `core/ → agent/`     | ✅ 仅惰性访问器               | `core/catalog.py` 提供函数级惰性读取内置子代理目录，模块加载期不触碰 agent                                                               |

`services/ → agent/` 原本有 9 处反向依赖，现已收敛到 6 处（含 P2 范畴的 `llm.factory` /
`tracing` / `mcp.adapter`——它们是 LLM/MCP/可观测**基础设施**，未来若要彻底消环需下沉到 `core/`，
但那会把 Agent 基础设施迁出 `agent/`，与「把 agent 当整体使用」的项目定位冲突，故保留现状）。

### 3.3 数据架构

三层数据模型，职责严格分离：

```
① 文件（内容事实源）        data/workspaces/{project_id}/
                            ├── novel.yaml         项目元信息 + 项目级 llm_params + outline_file
                            ├── volumes.yaml       卷列表（id 短 uuid 恒定 / title / sort_order★插入维护）
                            ├── chapters/v{vol}/c{ch}.md
                            │                      frontmatter: title / sort_order★插入维护 / word_count
                            │                        / status(draft|finalized) / version(乐观锁) / updated_at
                            ├── outline/{小说名称}-大纲.md   单文件大纲（★参考资料，不回填顺序）
                            └── summaries/ch-{chapter_id}.md 章节摘要（仅 summarize_chapter 可写）

                            data/recycle/{project_id}/      回收站（最多 20 本）
                            ├── index.yaml       被删条目索引（章名 / 所属卷 / 删除时间 / novel_deleted / trash_dir）
                            └── chapters/c{id}.md  章级删除的正文快照（整本删除不复制，见 trash_dir）
                            data/trash/{project_id}-{ts}/   整本软删除时搬走的工作区原件
                            data/skills/{name}/SKILL.md     用户技能物化目录
                            data/session-skills/{sid}/      会话选中技能的物化副本
                            data/exports/                   导出任务产物（zip）

② SQLite（结构化登记）      data/app.db —— 16 张表
                            登记 / 修订快照 / 会话 / 消息树 / 运行 / 中断 / 审计 / 配置 / 派生索引
                            data/agent_state.db —— LangGraph checkpoint（跨库不建外键）

③ 派生索引（可从①重建）     story_fts（FTS5 虚拟表，二元切分 + unicode61）
                            project_index（章数 / 总字数 / last_updated / dirty 脏标记）
```

**关键设计**：正文与知识库以 Markdown 文件为唯一事实源；`novels` 表只做项目登记与外键锚点
（可从工作区扫描全量重建）；派生索引失败不阻断写入，改标 `dirty=1` 待重建。

16 张表按域拆分：

| 域         | 表                                                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `novel`  | `novels` / `chapter_revisions` / `reading_progress` / `project_index`                                                                               |
| `agent`  | `agent_sessions` / `messages` / `tool_call_logs` / `agent_runs` / `agent_interrupts` / `subagent_configs` / `skill_configs` / `mcp_servers` |
| `llm`    | `llm_providers` / `llm_models`                                                                                                                          |
| `config` | `user_settings` / `audit_logs`                                                                                                                          |

**全局 ORM 约定**：所有 `id` 为 TEXT(uuid4) 应用层生成（不用自增整数）；时间戳一律 UTC ISO-8601
文本应用层写入；JSON 列统一命名 `*_json` 存 TEXT；枚举用 TEXT + 应用层校验；
连接建立时 `PRAGMA foreign_keys=ON` + WAL；命名约定集中在 `Base.metadata.naming_convention`
（使 alembic autogenerate 稳定生成约束名）。

**通用约定**：

- 统一响应包装 `{code, message, data}`，HTTP 状态码与 `code` 对齐（成功 `code=0` + 2xx）；
- 错误码常量集中在 `core/errors.py`，配 `CODE_TO_HTTP` / `CODE_TO_MESSAGE` **双映射表**：

| code      | HTTP | 含义                                                    |
| --------- | ---- | ------------------------------------------------------- |
| `0`     | 2xx  | 成功                                                    |
| `40001` | 400  | 参数格式错误                                            |
| `40301` | 403  | 越权（WorkspaceGuard 拒绝 / 跨项目写入）                |
| `40401` | 404  | 资源不存在                                              |
| `40901` | 409  | **版本冲突**（乐观锁失败，`data` 回传最新内容） |
| `40902` | 409  | 运行状态冲突（如对已结束 run 发 resolve）               |
| `41001` | 410  | SSE 事件缓冲丢失（前端应重拉消息树）                    |
| `42201` | 422  | **显式命名校验失败**                              |
| `42202` | 422  | 大纲解析失败                                            |
| `50001` | 500  | 服务端内部错误                                          |
| `50201` | 502  | LLM Provider 调用失败（含降级链耗尽）                   |
| `50301` | 503  | 依赖不可用（calibre 缺失 / MCP 探测失败 / FTS5 不可用） |

- SSE 信封 `{event, run_id, session_id, seq, ts, data}`，`seq` 每 run 内单调递增。

#### 4.1.5 关键功能流程设计

**① 正文保存与版本冲突（乐观锁 UX）**

```
打开章 → 记录 version 为 base_version → 编辑（dirty）→ 保存（手动/自动）携 base_version
  ├─ 200 → 更新本地 version，冲突清除
  └─ 409/40901 → ConflictBanner 弹出：展示服务端最新内容/版本/更新时间/最后写入方(manual|agent)
       ├─ 「查看差异合并」→ 对比后手工整合再保存
       └─ 「以我的为准」→ 携服务端最新 version 强制覆盖
```

**② 选区 AI 改写**：选中文字 → 四按钮（改写/扩写/缩写/润色）启用 → 调后端取结果（**不落盘**）
→ RewriteDiffDialog 句级 LCS 三色 diff 预览 → 「接受」替换选区并打 **AI 来源标记**
（Mark 扩展，点击标记可回滚为原文）/「放弃」丢弃结果。

**③ AI 改动章节的热更新**：Agent 写文件 → SSE `file.changed` → 工作台刷新卷章树；
若改的正是打开中的章：本地无未保存修改 → 静默重载；有 → 确认框「载入 AI 版本 / 保留本地修改」
（保留本地则后续保存自然进入 ① 的 409 冲突流程，不丢稿）。

**④ 流程生成（生成本章）**：目录选中章 → 右栏「生成本章」→ 确认框（说明四阶段与快照可回滚）
→ 流程状态条实时显示 S0→S3 流转；S0/S1/S3 不过 → ConsultCard 让用户拍板
（代写大纲 / 去补简介 / 强制跳过 / 认可现状…）；S2 期间高危写入 → ApprovalCard。

**⑤ 对话运行与分支**：发消息 → 202+run_id → SSE 流式渲染（token/工具/泳道/计划/用量）→
run.end 后重拉落库消息合并（重拉同时清空流式缓冲，否则同一条回复会显示两次）；
运行中可「停止」（协作式取消，由发送区的红色停止方块承担）。
★消息树的**兄弟分支**能力（`POST /agent/sessions/{sid}/branch` + `store.switchBranch`）**后端与 store 保留**，
但 面板已移除「重新生成」入口，故 UI 上暂不暴露分支切换；用户消息的乐观回显带时间戳（`pendingUserMessage` 记 `sentAt`）。

**⑥ 导出成书**：项目右键「导出」→ ExportDialog 选格式（markdown/epub/mobi/txt，mobi 在
calibre 未装时置灰+提示）→ 启动任务显示进度条 → 完成后「下载」zip（含大纲原件）。

#### 4.1.6 前端状态与通信设计

**Pinia 五 store 分工**（跨组件共享的最小状态集）：

| store        | 职责                                                                                                                                                                                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `project`  | 项目列表 / 当前项目 / 卷章树（`volumeTree` 按 sort_order 只读排序）/ 展平章序列 `flatChapters`（翻页用）/ 卷 CRUD                                                                                                                                                          |
| `editor`   | 打开章的 draft + base_version（乐观锁）/ dirty / 自动保存 / 409 冲突态 `conflict` / 修订快照列表与回滚 / 定稿状态 / **回退编辑栈**（`undoStack` 上限 5 条、`canUndo`、`pushUndoSnapshot`/`requestUndo`/`popUndoSnapshot`，换章与 reset 时清空）              |

- `api/http.ts`（axios）：统一拆 `{code,message,data}` 信封；按业务码分发 UI 行为
  （40901→ConflictBanner、40902→「运行已结束」提示、42201→命名错误、50301→依赖不可用警告）；
- `api/sse.ts`（EventSource）：断线自动重连带 `Last-Event-ID`；手动重连走 `?last_event_id=`；
  收到 `error(41001)`（缓冲丢失）回落重拉消息树；
- `api/index.ts`：89 个端点的类型化封装（与 `types/index.ts` DTO 一一对应；后端另有 `/audit`、`/export-preflight` 两个服务端点暂无 UI 调用）；

### 4.2 后端服务设计

前端每个功能背后，都需要后端给出一个**可信的承诺**：不丢稿、不错乱、可回滚、可追溯。
本节讲这些承诺是怎么被设计出来的。

#### 4.2.1 一个核心判断：谁是事实源

写作工具最怕的是「我写的东西不见了」。要回答这个问题，先得决定**当数据打架时听谁的**。

本项目的选择是：**文件是唯一事实源，数据库只是登记簿与索引**。

```
正文 / 大纲 / 摘要  →  Markdown 文件（事实源，人能直接打开看）
项目登记 / 会话 / 审计 →  SQLite（结构化查询用）
全文检索 / 字数统计  →  派生索引（可以随时从文件重建）
```

这个选择带来三个直接好处：

| 好处             | 说明                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **可逃生** | 即使数据库全毁，`data/workspaces/` 下的 `.md` 文件仍是完整的书稿，用任何编辑器都能打开                                     |
| **可重建** | 索引坏了不用慌，`writer rebuild-index` 扫一遍文件就回来了；派生索引写失败也**不阻断正文保存**，只标 `dirty=1` 待重建 |
| **可审计** | 文件在 Git 里能 diff，AI 改了什么一目了然                                                                                      |

代价是必须维护两套存储的一致性，因此有了下一条设计。

#### 4.2.2 不丢稿的三重保险

「保存」这个动作，在本项目里不是简单的 `UPDATE ... SET content=?`，而是三层保护叠加：

**① 乐观锁 —— 防止互相覆盖**

场景：你在编辑器里改第三章，同时 AI 也在写第三章。谁后保存谁赢？都不对——**先保存的人的稿子会被冲掉**。

做法是每章 frontmatter 里存一个 `version`：

```
打开章节 → 记住 version=5（base_version）
   ↓ 编辑…
保存时带上 base_version=5
   ├─ 文件里还是 5 → 写入，version 变 6 ✓
   └─ 文件里已是 7 → 拒绝（409/40901），并把「最新版本 + 是谁写的」回传
```

关键细节：回传的 `last_writer` 会告诉前端**是人改的还是 AI 改的**，前端据此弹冲突横幅让你选「看差异合并」还是「以我的为准」。**绝不静默覆盖**。

**② 修订快照 —— 让「后悔」成为可能**

每次有意义的写入前，先把旧内容存进 `chapter_revisions`。所以 AI 写完一章你不满意，可以一键回滚；定稿时也会留一份。

这里有个刻意的取舍：**自动保存不产生快照**。否则一边打字一边存，几分钟就能刷出几百条无意义的版本，真正想回滚时反而找不到。快照只在「手动保存 / Agent 写入前 / 章节定稿」三个时刻产生，并只保留最近 20 条。

**③ 单一写入口 —— 让规则无法被绕过**

所有文件写入都收敛到 `WorkspaceGuard` 一处。它不只是校验路径，更是**唯一能碰磁盘的地方**，因此：

- 越权路径（`..`、符号链接、跨项目）在这里被统一拦下；
- 审计埋点在这里统一打上；
- 派生索引同步在这里统一触发。

「规则写在多个地方」是这类系统最常见的腐化路径——总有一处忘了加校验。收敛到一处，就没有「忘了」的可能。

#### 4.2.3 顺序为什么不给用户拖拽

卷章的排列顺序，在很多编辑器里是可以拖拽的。本项目**故意不提供**：没有拖拽、没有「上移/下移」按钮、连 API 都没有 reorder / move 端点。

理由是**顺序只能有一个事实源**。如果同一个卷章树存在两种改顺序的途径（拖拽 + 别的写入），两者迟早打架，而且没人说得清该信哪个。

本项目的做法（调整）：**「插入」是唯一的位置编辑入口**。新建卷/章时可以指定序号，插入到第 k 位则第 k 位及其后各项顺延 +1；删除后其后各项重新连续编号。位置在创建那一刻就确定，之后只能靠插入新的卷章来「挤」出空间，不能拖着改。

> 之前顺序由大纲小节先后派生（保存大纲回填 `sort_order`）。实测下来这条链路对用户是黑盒——大纲改一个字，卷章树顺序就变了，还容易产生「大纲有、树里没有」的漂移。所以 把**大纲降级为参考资料**（仍是 AI 生成正文的重要依据），顺序改由插入维护；`sync_order_from_outline` 保留为只读诊断（报告大纲与实际结构的差异，不写盘）。

插入序号本身是**元数据**而非正文变更，所以调整序号不产生修订快照、不递增 `version`，避免和乐观锁、自动保存互相干扰。

这条约束还被写成了代码里的守卫函数 `assert_no_manual_reorder()`，配套测试断言「禁止出现的函数名」与模块实际导出**无交集**。谁想加个 reorder 接口，测试会先失败。

#### 4.2.4 为什么写作业务不交给 Agent

这是本项目最重要的一个职责划分：

```
写作业务（建项目、改标题、定稿、导出、检索）→ REST 接口，前端调用
内容本身（读章节、写正文、改文字）        → Agent 用文件工具
```

也就是说，**Agent 手里没有「删除章节」这种业务工具**，它只有读写文件的能力。

为什么这么设计？因为 Agent 的工具是模型自己决定调不调的，一旦把业务操作做成工具，就等于把「删库」的按钮交给了一个会犯错的概率系统。而收窄成文件读写之后：

| 收益                 | 说明                                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **越权面变小** | 框架的 `permissions` 只管内置文件工具，自定义工具它管不着。自定义工具中除 6 个结构操作（受 WriteApproval + WorkspaceGuard 双层守卫）外均不碰路径，盲区收窄到最小 |
| **可预测**     | 业务操作走 REST，参数校验、事务、错误码都是确定性的，能单测                                                                  |
| **可回滚**     | Agent 只能改文件，而所有文件写入都留快照                                                                                     |

同理，**流程的 S0/S1/S3 判定也不进 Agent 循环**，而是服务层直连模型要一个 JSON 结论。「检查大纲有没有写简介」这种事，需要的是稳定的是非题，不是自由发挥。

#### 4.2.5 取数与推流的分离

后端对前端提供两种通道，各管一件事：

| 通道           | 用途                             | 特点                  |
| -------------- | -------------------------------- | --------------------- |
| **REST** | 取数、控制（发消息、保存、配置） | 请求-响应，有明确结果 |
| **SSE**  | 推送运行过程（AI 正在写什么）    | 单向长连接，事件流    |

发一条消息给 AI，走的是「REST 下单 + SSE 收货」：

```
POST /messages  →  立刻返回 202 + run_id（不等 AI 写完）
GET  /runs/{id}/stream  →  订阅这个 run 的事件流
```

这样设计是因为 AI 生成可能持续几分钟，一个 HTTP 请求挂那么久既容易超时，也没法中途展示进度。

SSE 还会断线（切后台、网络抖动），所以每个 run 在服务端留一份 500 条的环形缓冲 + 单调递增的 `seq`。重连时带上 `Last-Event-ID`，服务端把漏掉的补发；**万一缓冲已被淘汰或进程重启，就明确回一个 `41001` 让前端重新拉一遍完整消息**，而不是假装什么都没发生。宁可多拉一次，不可悄悄丢事件。

#### 4.2.6 显式命名：一条产品级的硬约束

创建小说时，书名不能叫「未命名小说」；建卷时不能叫「第 1 卷」。这不是前端提示一下就算，而是**服务端校验 + 专用错误码 42201**。

理由很朴素：默认名会让工作区文件名、大纲标题、导出成品全都变成一堆无法区分的垃圾，而这些名字一旦生成就散落在文件系统各处，事后清理成本极高。与其事后治理，不如在入口拦住。

同一思路下，项目里还有几条「宁可让用户多点一下，也不留隐患」的约束：MCP 的 stdio 命令保存前要**弹窗展示完整命令二次确认**；密钥只写**系统级环境变量**（起；`.env` 已于 续移除）不进数据库，界面只显示 `sk-****abcd`。

### 4.3 Agent + Harness 设计

#### 4.3.1 先说清楚：什么是 Agent Harness

「Harness」原意是**马具**——套在马身上的那副挽具。马有力量，但往哪走、走多快、能不能踩进麦田，由挽具决定。

放到 AI 里，这个比喻精确得惊人：

```
大模型（LLM）      = 马       有强大的语言能力，但没有边界感、没有记忆、不会自己干活
Agent Harness      = 挽具     决定它能用哪些工具、看到哪些文件、什么时候必须停下来问人
Agent 应用         = 马车     挽具 + 马 + 车身，才是能载客的完整交通工具
```

一个**裸模型**只会「输入文字 → 输出文字」。要让它变成一个能改你硬盘上文件、能连续工作几分钟、出错能停下问你的助手，中间缺一整层东西：

| 缺什么               | Harness 提供什么                                                 |
| -------------------- | ---------------------------------------------------------------- |
| 它不能动手           | **工具层**：读写文件、执行搜索，以及「哪些工具对模型可见」 |
| 它不记得刚才干了什么 | **循环 + 状态**：多轮 tool call 的编排、断点续跑           |
| 它的上下文会爆       | **上下文治理**：摘要压缩、按需加载、预算监控               |
| 它会瞎搞             | **权限 + 沙箱**：路径白名单、危险操作拦截                  |
| 它是一次性的         | **人在环（HITL）**：中断、审批、恢复                       |
| 你不知道它干了啥     | **可观测**：trace、token 用量、评分                        |

**这一整层就叫 Agent Harness。** 本项目的第一个设计决策是：**这层不自研**。

#### 4.3.2 为什么不自研 Harness

自研一套 Agent 框架听起来很酷，实际是在和整个生态赛跑。本项目选择 **deepagents**（构建在 LangGraph 之上），理由：

- 上面那张表里的能力，deepagents 全都给了，且经过大规模验证；
- 自研的维护面会迅速超过业务本身——框架 bug 得自己修，新模型适配得自己跟；
- 本项目真正的价值在**写作领域**，不在通用 Agent 基建。

于是职责被清晰切成三层：

```
┌─────────────────────────────────────────────┐
│  ③ 本项目：写作领域化封装                     │
│     流程 S0→S3 / 前情提要 / 章节摘要          │
│     消息树分支 / 8 条权限规则 / 自定义中间件   │
├─────────────────────────────────────────────┤
│  ② deepagents：Agent Harness                 │
│     create_deep_agent / 沙箱 backend          │
│     permissions / subagents / skills          │
│     HarnessProfile（模型适配）                 │
├─────────────────────────────────────────────┤
│  ① LangGraph + langchain：图执行与模型抽象     │
│     astream / checkpointer / interrupt        │
│     AgentMiddleware 钩子                      │
└─────────────────────────────────────────────┘
```

**本项目只做 ③。** 判断某段代码该不该写，标准就一条：*它是在做「写作」的事，还是在做「通用 Agent」的事？* 后者一律交给框架。

#### 4.3.3 Harness 是怎么「套」上去的

装配一个 Agent，本质是给 `create_deep_agent()` 递一串参数。每个参数就是挽具上的一根缰绳：

| 参数              | 通俗理解         | 本项目的值                             |
| ----------------- | ---------------- | -------------------------------------- |
| `model`         | 用哪匹马         | 用户配置的模型（可多级降级）           |
| `backend`       | 它能看到哪片地   | `CompositeBackend`：3 条虚拟路径路由 |
| `permissions`   | 地里哪些能踩     | 8 条有序规则，兜底 `deny /**`        |
| `tools`         | 手里能拿什么     | 9 个自定义工具（含 6 个结构操作）+ 天气 MCP |
| `skills`        | 随身的操作手册   | 用户自建技能目录（渐进式披露）         |
| `subagents`     | 能叫来帮忙的人   | 4 个写作子代理 + recaller 记忆召回     |
| `middleware`    | 每一步要过的关卡 | 17 层固定顺序                          |
| `interrupt_on`  | 哪些动作要先问人 | `{}`（置空——删除风险由 WriteApproval 按参数判定） |
| `checkpointer`  | 记忆存哪         | `AsyncSqliteSaver`（独立库）         |
| `system_prompt` | 出发前的交代     | Jinja2 渲染的项目元信息 + 铁律         |

这里最值得展开的是**沙箱**和**权限**，因为它们决定了 AI 的「手」能伸多远。

#### 4.3.4 沙箱：让 AI 活在虚拟路径里

Agent 看到的不是 `E:\git\...\data\workspaces\{uuid}\chapters\v1\c3.md`，而是 `/projects/{pid}/chapters/v1/c3.md`。这层映射由 `CompositeBackend` 完成：

```
/projects/          →  data/workspaces/     写作内容（可读可写，跨项目只读）
/skills/user/       →  data/skills/         用户自建技能
/skills/session-{id}/ →  data/session-skills/{id}/   会话精选技能
其余（如 /conversation_history/）→ StateBackend（内存状态）
```

虚拟路径带来两个好处：**提示词里不暴露宿主目录结构**（模型不会学到你机器的路径习惯），以及**越权判定可以在虚拟层做完**（不必处理 Windows 盘符、符号链接、大小写这些脏活）。

还有一条硬约束：**绝不用 `LocalShellBackend`**。它会让 `execute`（执行任意命令）工具对模型可见——那是把 shell 交给概率系统。用 `FilesystemBackend` 时 `supports_execution()` 返回 False，deepagents 会**自动把 `execute` 从模型可见工具里摘掉**，连裁剪代码都不用写。

#### 4.3.5 权限：顺序即语义的 8 条规则

`permissions` 的判定机制有个反直觉的地方：**首条匹配生效，且无匹配时默认放行**。

这意味着规则顺序不是风格问题，而是安全问题——兜底的 `deny /**` 必须排在最后，一旦它跑到前面，后面所有规则全部失效，等于全线封锁；反之如果漏了它，就是全线放行。

本项目的 8 条规则表达的是一个很具体的产品意图：

| #    | 规则                                     | 意图                              |
| ---- | ---------------------------------------- | --------------------------------- |
| ①   | 当前项目 `/projects/{pid}/**` 读写     | AI 能改自己的书                   |
| ②   | 其它项目 `/projects/**` **禁写** | 但绝不能改别的书                  |
| ③   | 其它项目 `/projects/**` 可读           | 允许跨书参考（连贯性检查用）      |
| ④   | `/skills/**` 可读                      | 技能靠模型自己 `read_file` 加载 |
| ⑤   | `/skills/**` 禁写                      | 技能由服务层维护，AI 不许自我改造 |
| ⑥⑦ | 会话历史 / 大工具结果 可读写             | 上下文压缩的卸载区                |
| ⑧   | `/**` **兜底 deny**              | 其余一律不行                      |

②③ 组合起来就是设计铁律里的「**跨项目可读不可写**」；⑤ 则防住一个隐蔽风险：AI 若能改技能文件，就能给自己写新指令。

因为「首条匹配 + 默认放行」这个陷阱太容易踩，本项目把它**编码成常量 `PERMISSION_RULES` + 逐行断言的回归测试**，而不是只写在文档里靠人自觉。

#### 4.3.6 Harness Profile：框架层的模型适配

deepagents 提供了一套 **HarnessProfile** 机制，用来解决一个真实问题：**不同模型需要不同的调教方式**。

同样一句提示词，Claude 和 GPT 的反应可能完全不同；有的模型爱并行调工具，有的模型会过度思考；有的模型需要额外提醒「别滥用子代理」。这些差异不该由每个应用去适配，而应该由框架按模型统一给出。

HarnessProfile 就是这份「按模型定制的调教方案」，注册在 `provider` 或 `provider:model` 键上，能改四件事：

| 字段                                           | 作用                                                                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `system_prompt_suffix`                       | 追加模型专属提示（组装顺序：用户提示 → 框架基座 → **此后缀**，落在最靠近对话历史的位置）                       |
| `excluded_tools`                             | 对某个模型隐藏特定工具                                                                                                 |
| `extra_middleware` / `excluded_middleware` | 增删中间件（★`FilesystemMiddleware`、`SubAgentMiddleware` 是**脚手架，禁止摘除**，硬摘会抛 `ValueError`） |
| `general_purpose_subagent`                   | 调整自动追加的 `general-purpose` 子代理（关掉它，`task` 工具也随之消失）                                           |

deepagents 内置了几份 profile（Anthropic 三档、OpenAI Codex 系列、NVIDIA Nemotron 等），比如 Sonnet 4.6 那份会追加「独立工具调用请并行发起」「没打开过的文件不要猜」这类指导。

**本项目刻意不注册任何 HarnessProfile**，两个原因：

1. **匹配不上**。profile 按 `provider:model` 精确匹配，而本项目传给 `create_deep_agent` 的是**已构建好的 ChatModel 实例**（不是 spec 字符串），框架只能从实例上反推 provider 与 identifier。本项目用户常配的 Qwen / DashScope / OpenRouter 自定义端点，内置 profile 里没有对应项，注册了也不生效；
2. **不该在应用层替模型做主**。本项目已经用十余层中间件精确控制了运行行为（重试、降级、调用上限、上下文压缩、路径守卫、写入审批），再叠一层 profile 只会让「某个行为到底是谁加的」变得难查。

这是一个**有意的留白**：如果将来发现某个模型确实需要特殊调教，正确的做法是在 `builder.py` 的中间件栈里加一层，而不是注册 profile——这样行为归属清晰，也能被现有测试覆盖。

（想关掉自动追加的 `general-purpose` 子代理时，唯一途径就是 `GeneralPurposeSubagentProfile(enabled=False)`，它**不是 `create_deep_agent` 的普通参数**。本项目选择保持默认追加。）

#### 4.3.7 中间件：固定顺序的关卡

langchain 的 `AgentMiddleware` 只给了少数几个钩子（`before/after_agent`、`before/after_model`、`wrap_model_call`、`wrap_tool_call`），**没有** `before_tool` / `on_run_end`。这个限制直接决定了两个设计：所有工具级逻辑只能挂在 `awrap_tool_call`；运行收尾不能在中间件里做，只能等 `astream` 结束后统一 `finalize()`。

中间件的顺序不是随便排的，前一层是后一层的前提（起 `WriteApproval` 提到**最外层**）：

```
⓪ WriteApproval      ★最外层：参数级高危写入 → interrupt（harness/approval）
① ModelCallBudget    调用预算：超限先总结再 consult 询问继续/结束（取代旧 ModelCallLimit 的静默收尾）（harness/llm/call_budget）
② ModelRetry         模型超时/429/5xx/连接错误退避重试 2 次     ┐ harness/llm/resilience
③ ModelSwitchOnFailure 当前模型连续失败达阈值才切换备用模型      ┘ 装配
④ TodoList           给模型 write_todos 工具（计划可见）
⑤ RecapInjection     注入前情提要 + 预算检查（请求级，不回写 state）
⑥ HiddenContext      注入 run 级隐藏上下文（选区润色提示词）
⑦ ContextGuard       上下文两层保险第二层：provider 未命中时检查用户是否有明确获取指令
⑧ PairingRepair      工具消息配对自愈（多并行 tool call 错位修复）
⑨ WastefulLoopGuard  浪费型循环分级熔断（SOFT=3 次注入纠正/HARD=5 次注入换方向/工具层硬阻断）（harness/llm/wasteful_loop）
⑩ SteerInjection     注入运行中追加的引导消息
⑪ ReadScopeGuard     大纲/章节正文的读取授权守卫（harness/guard/read_scope）
⑫ WorkspaceGuard     ★路径校验 / 审计 / tool 事件 / 错误指纹阻断（harness/guard）
⑬ FileChangeNotify   文件变了 → 通知前端热更新 + 同步索引
⑭ ContentLock        写章正文时加 AI 编辑锁（harness/lock）
⑮ PromptCache        显式前缀缓存断点（DashScope/Anthropic 折扣计费，最内层）（harness/llm/prompt_cache）
```

①②③ 是**韧性层**（模型与成本），④⑤⑥⑦⑧⑨⑩ 是**上下文与循环治理层**，⓪⑪⑫⑬⑭⑮ 是**安全与协作层**。
架构优化：安全类中间件物理位置迁到 `harness/`（approval / guard / lock / llm），
`loop/middleware/__init__.py` 统一 re-export，装配顺序与语义不变。

此外还有两个辅助中间件在 builder 中按需装配：
- `ContextOverflowGuardMiddleware`（loop/middleware/overflow_guard.py）：设定 Context Length > 模型真实窗口时的兜底
- `ContextWindowSyncMiddleware`（loop/middleware/window_sync.py）：上下文窗口配置实时同步
- `SubagentContextScrubMiddleware`（subagents/scrub.py）：子代理结束时清空中间上下文
- `SafeDeleteMiddleware`（harness/sandbox/safe_delete.py）：把 Agent 的 delete 从永久物理删除改为可恢复删除（走回收站）

其中 ⓪⑫ 是本项目自研的，因为框架给不了：

- **⑨ WorkspaceGuard** 是权限的**第二道防线**。`permissions` 只作用于内置文件工具，自定义工具和 MCP 工具它管不着——这个盲区必须自己补。它还做了件框架没有的事：**错误指纹记忆**。同一个 `(工具, 参数哈希, 错误指纹)` 失败 2 次就注入告警提醒模型，3 次直接阻断该调用路径，防止模型在同一个坑里反复撞墙烧 token。
- **⓪ WriteApproval** 解决的是**参数级**审批。框架的 `interrupt_on` 只能做「这个工具要不要问人」的开关，但真正的危险不在于调了什么工具，而在于**用什么参数调**：`write_file` 覆盖一个空文件没事，覆盖一个 3000 字的定稿章节就是灾难。所以要自己判断——整章覆盖 / 超 800 字符的大范围改写 / 任何删除，才升级为人工审批。它必须装在**最外层**：`interrupt()` 抛出的 `GraphInterrupt` 若被外层中间件的 try/except 吞掉，会变成一条错误 ToolMessage，审批永远无法暂停 run。

#### 4.3.8 子代理与技能：分工与按需披露

**5 个内置子代理**（4 个写作子代理 + 1 个记忆召回），每个一个目录
（`subagents/builtin/{name}/spec.py + prompt.md`，提示词独立文件便于版本化与「恢复默认」）：

| 子代理           | UI 展示名    | 工种                                                                                         | 默认内置工具                                          | workflows 绑定                            |
| ---------------- | ------------ | -------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------- |
| `planner`      | Planner      | 策划大纲（三级大纲/分卷节奏/伏笔布局）                                                       | read_file / write_file / edit_file / ls / grep / glob | chapter-workflow（产出是 S0/S1 的输入）   |
| `writer`       | Writer       | 撰写修改**全流程**（原 writer+editor 合并：生成正文 + 润色校对）                       | read_file / write_file / edit_file / ls / grep / glob | chapter-workflow（S2 生成由它执行）       |
| `reviewer`     | Reviewer     | 大纲与小说内容**检查者**（原 continuity-checker 扩展：连贯性 + 大纲结构 + 简介匹配度） | read_file / ls / grep / glob                          | chapter-workflow + book-consistency-audit |
| `web-searcher` | Web_Searcher | 资料检索（原 researcher；name 用连字符是 deepagents 命名规则所限）                           | web_search                                            | —                                        |
| `recaller`     | Recaller     | 记忆召回（跨章节/跨卷的伏笔、人物状态、设定等上下文检索）                                    | read_file / ls / grep / glob                          | —                                        |

子代理的核心价值不只是「专业分工」，更是**上下文隔离**。默认 `mode=isolated` 意味着每个子代理在**自己的干净上下文**里干活，只把结论带回来。让 `reviewer` 去通读全书查伏笔，它消耗的巨量 token 不会污染主对话——这对动辄百万字的长篇是决定性的。派发语义：主 Agent 统筹决策 → 经 `task` 工具派发 → 子 Agent 独立执行 → 结果回传汇总。

**技能（Skills）** 则是另一种思路：**渐进式披露**。技能 = **用户自建**（无随包出厂技能），每个是一个 `SKILL.md`（物化到 `data/skills/{name}/`），挂载在虚拟路径 `/skills/user/` 下，但**不会一次性塞进提示词**。模型只在需要时自己 `read_file` 去读——这也解释了为什么权限规则 ④ 必须给 `/skills/**` 开读：关掉它，所有技能都变成不可见。

技能与子代理的组合关系：**子代理是「谁来干」，技能是「按什么章法干」**。两者都支持用户在「AI 设置」页自定义，也支持在会话级用上下文 Chips 精选（只带这次需要的）。用户自建子代理与内置功能重叠时**内置优先**（同名被 DB 唯一约束挡住；装配顺序内置在前）。

#### 4.3.9 流程：把「自觉」变成「必须」

这是本项目最具领域特色的设计。

「AI 写正文必须以大纲章简介为前提」——这条要求如果只写在提示词里，靠模型自觉遵守，结果必然是**时灵时不灵**：模型可能跳过检查，也可能反复重试不收敛。

所以本项目把它做成**服务层硬编排的四阶段状态机**，AI 没有选择权：

```
S0 大纲检查   →  这章在大纲里有小节和简介吗？
S1 前置校验   →  简介与上一章结尾接得上吗？
S2 生成正文   →  ★唯一进 Agent 循环的阶段
S3 后置校验   →  写出来的东西符合简介吗？
```

关键在**执行主体的切分**：

| 阶段         | 谁来执行                                         | 为什么                                                           |
| ------------ | ------------------------------------------------ | ---------------------------------------------------------------- |
| S0 / S1 / S3 | **服务层直连 ChatModel + JSON 结构化输出** | 这是是非题，要的是可预测、可单测、成本低。不需要工具，不需要多轮 |
| S2           | **deep agent 循环**                        | 这才真需要读写文件、调 writer 子代理                             |

「能用确定性代码解决的事，绝不交给概率系统」——这条原则贯穿全项目。

不过任何硬流程都会遇到「机器判断不了」的时刻，所以每道流程都能**发咨询卡片让人拍板**：S0 缺简介可以选「让 AI 代写大纲」或「我去补」；S3 连续 2 次不通过（`POSTCHECK_MAX_RETRY=2`）就交给人决定「认可现状 / 手动改 / 补充指示」。**上限 + 兜底咨询**，杜绝死循环。

#### 4.3.10 人在环：中断是可以存盘的

Agent 跑到一半需要问人，这在技术上是件麻烦事——进程不能一直挂着等。

本项目借助 LangGraph 的 `interrupt()` + `AsyncSqliteSaver` 把中断**持久化**：

```
AI 要覆盖整章 → WriteApproval 触发 interrupt
   ↓
状态存进 agent_state.db，run 置 awaiting_approval，SSE 推 interrupt.request
   ↓
（用户可能 5 分钟后才回来，甚至重启过服务）
   ↓
用户点「批准」→ POST /interrupts/{id}/resolve
   ↓
从 checkpoint 恢复，从中断处继续跑
```

审批支持**四种决策**，而不只是「同意/拒绝」：

| 决策        | 语义                                                         |
| ----------- | ------------------------------------------------------------ |
| `approve` | 原样执行                                                     |
| `edit`    | **改参数后执行**（比如把「覆盖全章」改成「只改这段」） |
| `reject`  | 不执行，告诉模型「用户拒绝了」                               |
| `respond` | 不执行，把用户的补充说明回给模型                             |

`edit` 和 `respond` 是体验上的关键——它们让「人和 AI 协作」而不是「人给 AI 当门卫」。

配套的两条保障：**取消是协作式的**（给 3 秒优雅退出窗口，超时才硬 cancel，避免留下半截文件）；**AI 写入前必先快照**（所以哪怕批错了也能回滚）。

#### 4.3.11 上下文治理：长篇才是真正的难题

写 3 章的 demo 谁都会做，写 300 章才是这个项目要解决的问题。核心矛盾：**模型上下文有限，而书会越来越长**。

本项目的答案是**分层替代**，而不是「把整本书塞进去」：

| 手段                       | 做法                                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **前情提要替代原文** | 每章定稿后生成结构化摘要（关键事件 / 人物 / 伏笔 / 结尾状态），后续章节只带摘要，不带原文                         |
| **跨卷锚点**         | 每卷第 1 章容易接不上，自动补一条「上一卷末章」锚点；第一卷则用大纲附录的人物/世界观设定                          |
| **按需精选**         | 会话级「已读章节」Chips，用户指定这次要参考哪几章（上限 8 章防膨胀）                                              |
| **预算监控**         | 可用量 = `max_context − reserve_for_output`(默认预留 4096 给输出)，超了发 `context.compact` 事件，前端能看到 |
| **摘要压缩**         | 触发时把驱逐的消息卸载到 `/conversation_history/`，而非直接丢弃                                                 |
| **增量化**           | checkpoint 用 `DeltaChannel(snapshot_frequency=50)` 存增量，不存全量                                            |
| **隔离**             | 子代理独立上下文（见 4.3.8）                                                                                      |
| **硬上限**           | `ModelCallBudget(60)` 软上限 + `recursion_limit(60)` 硬上限                                                    |

设计哲学是：**上下文是最贵的资源，每一段进入提示词的文字都要有明确理由。**

#### 4.3.12 可观测：看不见的东西没法改进

AI 应用最难的是「效果不好但不知道哪不好」。本项目接 **Langfuse**，三条链路：

- **自动埋点为主**：挂 langchain `CallbackHandler`，自动产出 trace / span / generation（含 token 用量）；
- **手动补充**：流程判定这类「服务层直连模型、不经过 Agent 循环」的调用，用 `observation()` 上下文管理器包裹，否则在 trace 里是看不见的；
- **评分回写**：run 结束写 `run_tokens` / `project_words` / `fallback_used` 三项 score。

流程的判定理由与分数也一并写入 observation——这意味着**「S1 为什么判不通过」是可回溯、可批量分析的**，为后续提示词调优提供真实数据，而不是靠感觉。

★未配置 Langfuse Key 时全链路自动 no-op 降级为本地结构化日志，功能不受任何影响。可观测是加分项，不能变成依赖项。

#### 4.3.13 一句话总结这套设计

```
把「通用能力」交给框架（deepagents Harness）
把「领域规则」做成确定性代码（流程、顺序、命名、乐观锁）
把「模糊判断」留给模型（写正文、查连贯、拟大纲）
把「不可逆动作」交给人（审批、咨询、快照回滚）
```

四条边界划清之后，一个会犯错的概率系统，就变成了一个可用的写作工具。

### 5.5 `api/` —— 路由层

15 个模块与 services **同名配对**（agent / audit / llm / mcp / novels / outline / recycle /
skills / story / subagents / volumes + chapters / settings / widgets / health），分层命名一致、无缩写。

`api/agent.py` 是唯一持有 Agent 运行入口的模块（`run_manager` + `sse_bus`），其 SSE 端点实现：
读 `Last-Event-ID` 请求头（EventSource 自动重连）或 `?last_event_id=`（手动重连，EventSource
无法自定义 header）取较大值 → `sse_bus.subscribe()` 拿 `(queue, backlog, lost, finished)` →
`lost` 则发 `buffer_lost_event`(41001) 并关流 → 先补发 backlog（遇 `run.end`/`error` 即返回）→
`finished` 则直接关流 → 否则循环 `wait_for(queue.get(), timeout=15)`，超时发心跳注释行
（`{"comment":"ping"}`，不占 seq）→ `finally` 里 `unsubscribe`。

`POST /sessions/{sid}/messages` 返回 **202 + `{run_id}`**（事件走独立 SSE 端点）；
若该会话已有活跃 run（`run_manager.running_ids()` + `session_of()` 匹配）→ 409/40902。
**全局单飞**：同一时刻只允许一个会话处于「AI 思考执行中」——其它会话发消息时
`run_manager.start()` 返回 None（不起 run），把用户消息与固定提示回复
（`GLOBAL_BUSY_REPLY` =「当前已有其他会话在进行AI思考哦，等任务完成后再聊吧~」）
一并落消息树，接口仍回 202 但 `data.run_id=null` + `data.rejected="global_busy"`，
前端刷新消息树即可看到 AI 的提示回复。

### 6.2 普通对话运行（发消息 → 流式回复）

```
前端 POST /agent/sessions/{sid}/messages
  │  （该会话有活跃 run → 409 / 40902）
  ▼
api/agent.py：services.agent.require_session 取会话行 → run_manager.start()
  ▼
loop/runner.py：用户消息入消息树（接 active_leaf 或按 parent_id 建兄弟分支）
  → 建 agent_runs(status=pending) → 会话置 running → sse_bus.open()
  → _spawn()（per-run asyncio.Lock 串行化）→ 立即返回 202 + run_id
  ▼
loop/resolve.py：解析主模型 + 降级链（未配模型 → 50201）
  → make_recap_provider（前情提要 + 会话「已读章节」Chips）
  → session_context_of（会话级子代理/技能 id → name）
  ▼
loop/builder.py：build_agent → create_deep_agent(backend, permissions, checkpointer,
                  tools, subagents, skills, 17 层 middleware, context_schema=AgentContext)
  ▼
lifecycle.graph_config() 生成 thread_id + recursion_limit
resolve.attach_langfuse() 挂 CallbackHandler
发 run.start 事件
  ▼
graph.astream(stream_mode=["updates","messages"], subgraphs=True, context=ctx)
  ▼
loop/streaming.py：逐 chunk 映射为 SSE
  ├─ namespace 首次出现 → subagent.start（子代理泳道开启）
  ├─ messages 模式 → message.delta / subagent.delta / usage
  └─ updates 模式 → __interrupt__ → 落 agent_interrupts + interrupt.request|consult.request
                  → model 节点完成 → message.complete / subagent.end
                  → 顶层 tools 节点完成 → 对所有活跃子代理发 subagent.end
                  → write_todos → plan.update
                  → ★消息树落库只在 astream 收尾（正常结束/中断暂停）做一次 force 同步：
                    中途思考/工具消息不再逐次持久化，避免「Agent 还没干完就冒出一条中间回复气泡」
                    （暂停期间已落库的消息由前端 collapseTurns + runPaused 继续隐藏）
  ▼
中间件并行生效（固定顺序，共 17 层）：
  WriteApproval（★最外层：参数级高危写入 → interrupt，GraphInterrupt 不能被吞）
  → ModelCallBudget（调用预算：超限先总结再 consult 询问继续/结束）
  → ModelRetry → ModelSwitchOnFailure（harness/llm/resilience 装配）
  → TodoList
  → RecapInjection（注入前情提要 + 预算检查 → context.compact）
  → HiddenContext（run 级隐藏上下文注入）
  → ContextGuard（上下文两层保险第二层）
  → PairingRepair（工具消息配对自愈）
  → WastefulLoopGuard（浪费型循环分级熔断）
  → SteerInjection（运行中追加的引导消息注入）
  → ReadScopeGuard（大纲/章节正文的读取授权守卫）
  → WorkspaceGuard（路径校验 + 审计 + tool.start/tool.result + 错误指纹阻断）
  → FileChangeNotify（file.changed + 同步派生索引；改大纲只重建索引，不再回填顺序）
  → ContentLock（写章正文加 AI 编辑锁）
  → PromptCache（显式前缀缓存断点，最内层）
  ▼

```

前端 `GET /agent/runs/{run_id}/stream` 订阅事件（先建流再发消息、或先发消息再建流都支持，
环形缓冲会补齐）。断线重连带 `Last-Event-ID`（或 `?last_event_id=`）从缓冲补发；
缓冲丢失 / 进程重启 → `error(41001)` 并关流，前端回落重拉消息树。

`tool.result` / `subagent.start` / `subagent.delta` / `subagent.end` / `plan.update` /
`file.changed` / `context.compact` / `workflow.update` / `consult.request` / `interrupt.request` /

### 6.3 流程生成运行（「生成本章」→ S0→S3）

```
用户请求生成第 N 章（POST messages 带 target_chapter_id）
  ▼
loop/runner.py 检测 target_chapter_id 非空 → 分流到 writing_steps/runner.py:execute_chapter_workflow
  ▼
还原或新建 WorkflowState（resume 且有 workflow_result_json → from_json 还原状态机位置）
  ▼
S0 大纲存在性（orchestrator，parse_outline 严格定位目标章简介小节）
  │  区分两类缺失（咨询文案不同）：① 无对应小节 → 引导按模板补小节
  │                              ② 小节存在但简介为空 → 引导填写简介
  │  ★两类均不自动插入占位小节
  │──无简介──▶ ConsultRequired(outline_missing) → consult.request
  │            （选项：让 Agent 代写大纲 / 我自己去「大纲」节点补 / 取消本次生成）
  │            → 运行置 awaiting_consult 暂停
  │            若选「代写大纲」→ 跑一次 agent 流写大纲 → 清 outcome 重查 S0
  │有简介
  ▼
S1 衔接预检（orchestrator 服务层直连 LLM + JSON 结构化输出）
  │  比对该卷各章简介的衔接合理性（因果/时间线/人物状态/伏笔承接）
  │  ★带入上一卷末章简介作锚点（否则每卷第 1 章无上文可校验；
  │    第一卷改用大纲附录的人物/世界观设定作锚点）
  │──不合理──▶ ConsultRequired(precheck) → consult.request（问题清单 + 修改建议）
  │            用户可改大纲后重跑，或「强制跳过」（需显式确认并落审计）
  │合理
  ▼
S2 生成（★唯一进入 deep agent 的阶段）
  │  prepare_generate() 组装生成指令（章简介 + build_recap，目标字数 agent_word_target=3000）
  │  writer 子代理用文件工具写入 chapters/v{卷}/c{章}.md
  │  ★syncer.skip_human_once = True（生成指令是内部消息，不入消息树）
  │  ★写入前 WriteApproval 判定整章覆盖 → 先快照旧正文进 chapter_revisions(source="agent")
  │  期间可触发参数级审批 → 持久化 WorkflowState → awaiting_approval
  │  正常结束 → state.stage = "S3" 继续
  ▼
S3 匹配后检（orchestrator 服务层直连 LLM）
  │  比对生成正文与该章简介的匹配度（要点覆盖 / 是否偏离 / 是否引入简介外重大剧情）
  │──不匹配──▶ 自动重生成（postcheck_retry ≤ POSTCHECK_MAX_RETRY=2，每次重生前同样先快照）
  │            仍不匹配 → ConsultRequired(postcheck) → consult.request
  │                       （认可现状 / 手动修改正文或大纲 / 补充指示后再生成）
  │匹配
  ▼
完成：summarize_chapter 生成摘要 → 更新派生索引 → stage=done → run.end
```

**执行主体分工**：S0/S1/S3 由 `writing_steps/orchestrator.py` 服务层直连 ChatModel 完成
（可预测、可单测、成本低，**不进入 Agent 循环**）；只有 S2 进 deep agent。
`agent_runs` 的 `workflow_stage` / `workflow_retry_count` / `workflow_result_json` 全程流转，
前端 `WorkflowStatusBar` 据 `workflow.update` 事件渲染。

**适用范围**：流程仅约束 **AI 生成正文**路径；用户手工编辑不受限。

### 6.4 中断与恢复（HITL）

```
Agent 触发中断（三类来源）
  ① 参数级：WriteApprovalMiddleware.classify_risk 命中 → langgraph.types.interrupt()
     （interrupt_on={} 已置空——删除卷章的风险确认由 WriteApproval 按参数判定）
  ② 流程咨询：orchestrator 抛 ConsultRequired
  ③ 预算级：ModelCallBudget 超限 → consult 询问继续/结束
  ▼
streaming._persist_and_emit_interrupt / writing_steps._persist_workflow_consult
  → 落 agent_interrupts(type=approval|consult, payload_json ≤20000 字符)
  → 发 interrupt.request | consult.request
  → run.status = awaiting_approval | awaiting_consult，会话同状态
  → publish_run_end({status, paused:true})
  ▼
前端渲染 ApprovalCard / ConsultCard → POST /agent/interrupts/{id}/resolve
  │  approval: approve | edit(带 edited_args) | reject(带 message) | respond(带 message)
  │  consult : option(带 choice) | text(带 text)
  │  （中断已处理 → 409；对已结束 run → 409 / 40902）
  ▼
services.agent.resolve_interrupt：校验 + 归一化为 langchain HITL batched resume 形状
  │  approve → {"decisions":[{"type":"approve"}]}
  │  edit    → {"decisions":[{"type":"edit","edited_action":{"name":<真实工具名>,"args":{...}}}]}
  │            ★name 必须是 agent 已注册的工具名（_apply_edit 会校验，传错抛 ValueError）
  │  reject  → {"decisions":[{"type":"reject","message":...}]}
  │  respond → {"decisions":[{"type":"respond","message":...}]}
  → 落库决定（decision/response_json/decided_by/decided_at）+ 审计
  → run 与会话置 running → 返回 {run_id, resume_value}
  ▼
api 层 asyncio.create_task(run_manager.resume(...))（不阻塞响应）
  ▼
sse_bus.reopen()（finished=False，seq 续增，缓冲保留 → 客户端无缝续传）
  → Command(resume=...) 续跑同一 run（thread_id 不变）
  → ★**中断挂起一律按 id 定向**（`lifecycle.resume_input_for` 构造「langgraph interrupt
    id → 值」映射；模型并行发多个高危调用时更是 langgraph 的硬性要求）：
    本次已决中断 → 其 resume_value；**已决但值未送达的兄弟中断** → 用落库 response
    一并送达（否则其 DB 行已决而 checkpoint 仍 pending，卡片不再出现、run 永久挂起）；
    未决兄弟不放入映射 → 保持挂起，run 再次暂停并展示剩余卡片。
    id 定位：行 payload 的 `langgraph_interrupt_id`（流事件补记），缺失时读 checkpoint
    快照按 `tool_call_id`/`consult_kind` 匹配；checkpoint 无挂起中断时沿用标量。
  → ★**失败关闭（fail-closed）**：本次决定对不上任何挂起中断时，若库里还有**另一张未决卡**
    正对应某个挂起中断，则绝不把这个决定投递给它——返回一个匹配不到任何命名空间的
    占位键映射（`_UNMATCHED_RESUME_KEY`），langgraph 忽略之，对应任务重放时再次
    `interrupt()` 挂起，用户仍会看到那张真正待批的卡。
    回归动因（并行工具调用竞态）：某任务的 `interrupt()` 被取消时，审批卡已建而中断未落
    checkpoint（「幽灵卡」）；用户批准它时若退回标量（langgraph 记为全局 null_resume）或
    「唯一挂起就给它」，该批准会被**另一个**高危写入当成自己的答复直接执行——
    未经批准就删了章节。仅当挂起中断在库里没有对应未决卡（无从区分身份）时，
    才定向投递给唯一挂起者，以免 run 永久停在 awaiting_*（无卡可点）。
  → ★固定流程运行按 state.pending_consult 路由：
      属三种咨询类型 → 走流程 resume_decision
      否则（approval）→ 包成 langgraph Command 给 S2 流内处理
```

### 6.5 取消

```
POST /agent/runs/{id}/cancel
  ▼
置 cancel_flags[run_id]["cancelled"] = True（★协作式：当前工具/模型调用返回后才停）
  → run 置 cancelling
  ▼
给 3 秒优雅窗口：await wait_for(shield(task), timeout=3.0)
  超时/异常 → task.cancel() 硬取消
  ▼
deepagents 内置 PatchToolCallsMiddleware 自动修复被截断的消息历史
  ▼
run 置 cancelled + ended_at，会话回 idle → 发 run.end({"status":"cancelled"}) → sse_bus.close()
```

`stream_graph` 每处理一个 chunk 都检查 `cancel_flag`，命中即置 `result.cancelled` 并 break。

### 7.3 langchain 1.4.7 中间件钩子的真实边界

`AgentMiddleware` **只有**：`before_agent` / `after_agent`、`before_model` / `after_model`、
`wrap_model_call`、`wrap_tool_call`（各带 `a*` 异步版）+ `name` / `state_schema` /
`trace_policy` / `transformers`。

★**没有** `before_tool` / `after_tool` / `on_node_end` / `on_run_end`。这一约束直接决定了本项目两个设计：

1. 工具级校验/审计/通知全部落在 `awrap_tool_call`（4 个自定义中间件都挂这里）；
2. **运行收尾不在中间件里做**，由 `loop/lifecycle.py:finalize()` 在 `astream` 结束后统一执行。

### 7.4 关键算法与数据结构

| 主题                     | 方案                                                                                                                                                                                                                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **中文全文检索**   | FTS5 `tokenize='unicode61'` + **手工二元切分**（`少年走出山村` → `少年 年走 走出 出山 山村`）。★`trigram` 对 2 字词**零命中**（`MATCH '少年'` 返回 0 行，3 字起才命中），不能作主方案。索引侧与查询侧**必须用同一个 `bigram_tokenize()`**，否则永远查不到 |

| **大纲解析**       | 严格层级正则 `^#(?!#)\s+(.*)$` / `^##(?!#)\s+(.*)$`（★宽松正则会把 `## 第三章 卷土重来` 误判为卷节）；附录节（`^附录`）下的 H2 不参与章匹配；卷章名**归一化后完全相等**才算命中                                                                                            |

| **SSE 断线续传**   | 每 run 内存环形缓冲 `deque(maxlen=500)` + `seq` 单调递增 + `Last-Event-ID` 补发；缓冲淘汰或进程重启 → `41001` + 关流 + 前端重拉消息树                                                                                                                                            |

| **上下文治理**     | token 预算（`max_context × 0.5`）+ 前情提要替代逐章原文 + `DeltaChannel` 增量 checkpoint + summarization 驱逐卸载 + 子代理上下文隔离（`mode=isolated`）+ `ModelCallBudget(60)` 软上限 + `recursion_limit(60)` 硬上限                                                            |

## 八、开发重难点

### 8.1 ★难点一：流程编排与 Agent 循环的职责切分

**问题**：AI 生成正文必须以大纲章简介为前提，但「让 Agent 自觉检查大纲」不可靠——
模型可能跳过检查、也可能反复重试不收敛。

**方案**：**服务层硬编排**为四阶段状态机（非 Agent 自觉执行），且按「可预测性」切分执行主体：

- S0/S1/S3 = **服务层直连 ChatModel + JSON 结构化输出**（不进 Agent 循环）→ 可预测、可单测、成本低；
- S2 = **唯一进入 deep agent 的阶段**（需要文件工具与 writer 子代理）。

**踩坑与对策**：

| 坑                                                                                                     | 对策                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 状态机要跨中断恢复（咨询暂停 → 用户回复 → 从原阶段续跑）                                             | `WorkflowState` 序列化进 `agent_runs.workflow_result_json`；resume 时 `from_json` 还原；★用 `state.pending_consult` 记录**是哪种咨询**，resume 时据此路由：属三种咨询类型走流程 resume，否则包成 `langgraph.types.Command` 交给 S2 流内处理 |
| resume 值的形状不统一（流程咨询 vs langchain HITL batched）                                            | `resolve_interrupt` 统一归一化为 `{"decisions":[Decision]}`；流程侧 `_extract_consult_decision` 提取 `{decision, choice, text}`                                                                                                                      |
| S3 反复重生成不收敛（死循环）                                                                          | `POSTCHECK_MAX_RETRY=2` 上限 + 每次重生前快照（可回滚）+ 仍不匹配发咨询卡片兜底（认可现状/手动修改/补充指示）+ S1「显式确认跳过」落审计                                                                                                                    |
| 流程功能被劈成两半（状态机在 `writing_steps/`、运行编排在 `loop/runner.py`），读流程必须跨文件跳转 | 把 `_execute_chapter_workflow` 及其 3 个辅助函数整体迁入 `writing_steps/runner.py`，与 `orchestrator.py` 同住                                                                                                                                          |
| S2 的生成指令是**内部消息**，不应出现在用户可见的消息树里                                        | `MessageSyncer.skip_human_once` 标记：跳过下一条 human 消息（只推进索引指针，不落库）                                                                                                                                                                      |
| S0 缺失有两种语义（无小节 vs 小节存在但简介为空），咨询文案应不同                                      | `parse_outline` 区分两类，咨询卡片分别引导「按模板补小节」与「填写简介」；★两类均**不自动插入占位小节**（避免污染用户大纲）                                                                                                                         |
| S1 校验每卷第 1 章时无上文可比                                                                         | 带**上一卷末章简介作锚点**；第一卷改用大纲附录的人物/世界观设定作锚点                                                                                                                                                                                  |

### 8.2 ★难点二：流式事件的完整映射与断线续传

**问题**：LangGraph 的 `astream` 输出是 `(namespace, mode, payload)` 三元组流，与前端需要的
语义事件（消息增量、工具调用、子代理泳道、待办计划、流程流转、审批卡片）之间没有现成映射；
且 SSE 会断线、进程会重启，事件不能丢。

**方案**：

- **双 stream_mode**：`["updates","messages"]` —— `messages` 拿 token 级增量，`updates` 拿节点完成与中断；
- **`subgraphs=True`** 拿子代理事件，用 `namespace` 区分泳道（`_subagent_name()` 从形如
  `("task:planner",)` 或 `("planner:xxxx",)` 的 namespace 提取名字）；
- **泳道生命周期**：新 namespace 首次出现 → `subagent.start`；顶层 `tools` 节点完成 → 对所有
  活跃子代理发 `subagent.end`（★顶层完成是子代理结束的唯一可靠信号）；
- **环形缓冲 + seq**：每 run 一个 `deque(maxlen=500)`，`seq` 单调递增；`subscribe(run_id, last_event_id)`
  返回 `(queue, backlog, lost, finished)` 四元组，`lost` 判定为请求位点已被淘汰；
- **两种重连方式**：`Last-Event-ID` 请求头（EventSource 自动重连）或 `?last_event_id=`
  （手动重连，★EventSource 无法自定义 header）；取两者较大值；
- **先建流/先发消息都支持**：`POST messages` 返回 202 后，连接前产生的事件由环形缓冲补齐；
- **不可续传时明确失败**：发 `error(41001)` 并关流，前端回落重拉消息树（★不做静默丢事件）；
- **心跳保活**：`wait_for(queue.get(), timeout=15)` 超时发 `{"comment":"ping"}`
  （★SSE 注释行，不占 seq，不影响续传位点）；
- **`reopen()` 无缝续跑**：中断恢复时 `finished=False`、`seq` 续增、**缓冲保留**，客户端无需重连。

### 8.3 ★难点三：消息树的双轨一致性与增量同步

**问题**：消息既要给前端渲染/审计/导出（业务库），又要给 LangGraph 恢复运行（checkpoint）；
而 graph state 里的消息 id 由 LangGraph 生成，与业务库 uuid **无对应关系**。

**方案**：

- **双轨持久化**：业务库 `messages`/`tool_call_logs`/`agent_runs` + LangGraph `AsyncSqliteSaver`
  （`data/agent_state.db`，与业务库分离，跨库不建外键），以 `run_id`/`thread_id` 关联；
- **★索引基线增量同步**（不按 id 匹配）：利用 state 的 messages 是**追加式**的这一性质，
  只记「已同步到的下标」，每次 sync 只处理新增部分；
- **基线确定**：首轮用户消息已由 API 层落库、state 里它将成为 `messages[0]` → 基线 = 1、
  parent = 该消息 id；恢复时中断前消息已全部落库 → 基线 = 当前 state 长度、parent = 会话 `active_leaf_id`；
- **未完成消息不落库**：`status=="streaming"` 或（无内容且无 tool_calls）视为未完成，留待下次 sync；
  中断时 `force=True` 强制落库已产生的消息；
- **分支语义**：`parent_id + branch_index`，同父下新增消息即成兄弟分支；
  构造 LLM 上下文时**只取 `root → active_leaf` 的活跃路径**；
  面板移除了「重新生成」按钮，分支机制与 `switchBranch` 接口保留（后端能力不减）；
- **checkpoint 体积**：`DeltaChannel(snapshot_frequency=50)` 增量存储 → O(N) 而非 O(N²)；
- **checkpointer 必须进程内单例**：aiosqlite 连接须长生命周期持有（每个 run 重开会丢中断态）；
  `asyncio.Lock` + 双检；`DATA_ROOT` 变化时自动重开（★否则测试会串库）。

### 8.4 ★难点四：权限「首条匹配 + 默认放行」的顺序陷阱

**问题**：deepagents `FilesystemPermission` 的判定机制是**首条匹配生效、无匹配默认 `allow`**
（`_check_fs_permission` 返回 allow）。这意味着规则顺序写错就会**全线放行**，且不会报错。

**方案**：

- 8 条规则以 **`PERMISSION_RULES` 常量数组**集中定义，每条带注释说明意图；
- **兜底 `deny /**` 必须最后**；新增规则只能插在兜底之前；
- ★把设计约束**编码成常量 + 配回归测试**：`tests/test_permissions.py` 逐行断言常量数组与设计表一致
  （顺序回归测试），并对每条规则做越权用例（读其它项目允许、写其它项目拒绝、写技能拒绝、
  兜底拒绝等）；
- **第二道防线**：`permissions` 只作用于内置文件工具，自定义工具/MCP 不在其覆盖范围 →
  `WorkspaceGuardMiddleware` + `services/workspace.WorkspaceGuard` 兜底；
- ★`delete` **归入 `write` 权限**（deepagents 的 `operations` 只有 `read`/`write`），
  故「删其它项目文件」会被第 2 条 `write deny` 拦下；
- ★`/skills/**` 必须开 `read allow`：技能靠模型 `read_file` 读 `SKILL.md` 渐进式披露，
  漏开 read 会导致**技能全部静默不可用**（配套集成测试断言 Agent 能读到用户技能全文）。

### 8.5 ★难点五：中文全文检索

**问题**：SQLite FTS5 默认分词器对中文无效（整段当一个 token）；`trigram` 看似可行但实测
**对 2 字词零命中**（`MATCH '少年'` 返回 0 行，3 字起才命中），而中文小说检索大量是 2 字词。

**方案**：

- **手工二元切分 + `unicode61`** 为主方案：把中文切成空格分隔的二字词后存入 FTS5 列，
  非 CJK 片段（拉丁词、数字）原样保留交给 unicode61；
- ★**查询侧必须用同一个 `bigram_tokenize()`**，否则永远查不到（这是最易踩的坑）；
- `project_id` **必须入表且 UNINDEXED**：查询时附加 `AND project_id = ?` 过滤，否则跨项目串数据；
- **降级路径**：FTS5 不可用或查询异常时回落 `LIKE '%q%'`，★接口签名与返回结构不变
  （只多 `data.degraded=true`），前端无需分支处理；
- **两步探测**（见 7.4）确保降级判定可靠且只探一次；
- 不使用向量库（零 Embedding 费用、零额外服务）；数据源为大纲单文件 + `summaries/`；
  ★检索**不作为 Agent 工具**（Agent 用内置 `grep` 搜文件），避免两套检索语义漂移。

### 8.6 ★难点六：并发写入与内容一致性

**问题**：自动保存（前端定时）、Agent 写章（后台任务）、流程重生成可能同时改同一章；
Agent 改文件后派生索引可能与文件不一致；卷章顺序若有两个来源会漂移。

**方案**：

| 风险                                                         | 对策                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 8.7 ★难点七：第三方生态的版本兼容性

**问题**：deepagents / langchain / mcp / langfuse 都是快速演进的库，文档与实装常有差异，
且仓库里的 `demo/` 脚本用的是旧版 API。

### 8.8 ★难点八：Windows 平台的编码与路径

**问题**：项目在 Windows 上开发运行，路径分隔符、非法文件名字符、编码默认值都是坑。

**方案**：

- 路径解析**全部集中**在 `core/paths.py`，一律 `pathlib.Path`；
- 文件读写**显式 `encoding="utf-8"`**（`write_text()` / `read_text()` 统一入口），
  Jinja2 `FileSystemLoader` 也显式传 `encoding="utf-8"`；
- `safe_filename()` 替换 Windows 非法字符（反斜杠、斜杠、冒号、星号、问号、引号、尖括号、竖线）
  与控制字符为 `_`，并压缩连续空白；
- SQLite URL 需把 Windows 路径**转正斜杠**（`path.as_posix()`）；
- `WorkspaceGuard` 拒绝含 `..` 的路径、逐段检查符号链接解析后是否越界；
- ★虚拟路径 → 宿主路径转换时统一把反斜杠归一化为正斜杠；
- `main.py` 启动器区分 `os.name == "nt"` 处理子进程信号与命令构造。

### 8.9 ★难点九：长篇上下文治理与成本控制

**问题**：长篇小说逐章累积，若把历史章节全塞进上下文会爆窗口且成本失控。

**方案（多层组合）**：

1. **前情提要替代原文**：`build_recap` 只给近 6 章**摘要**（无摘要则正文节选 ≤600 字）+
   书名/题材/梗概 + **跨卷衔接锚点**；
2. **章节摘要自动生成**：`summarize_chapter` 在章节定稿或 Agent 写完后生成结构化摘要
   （`key_events` 3-6 条、`characters`、`foreshadowing`、`ending_state`）；
3. **token 预算检查**：`budget_report` = `max_context × 0.5` 阈值，超则发 `context.compact`；
4. **summarization 驱逐卸载**：deepagents 版把被驱逐消息卸载到 `/conversation_history/{session_id}.md`
   （权限规则第 6 条专门放行）、预截断过大的 `write_file/edit_file` 参数、遇 `ContextOverflowError` 自动重试；
5. **子代理上下文隔离**：`mode=isolated`（默认），子代理不继承主代理全部上下文；
6. **调用次数双限**：`ModelCallBudget(run_limit=60)` 软上限（超限先总结再 consult 询问继续/结束）+
   `config={"recursion_limit":60}` 硬上限；
7. **checkpoint 增量存储**：`DeltaChannel(snapshot_frequency=50)` → O(N)；
8. **用量可观测**：`usage` 事件 + `agent_runs.tokens_in/out` + Langfuse score（`run_tokens` /
   `project_words` / `fallback_used`）供复盘调优；
9. **裁剪优先级**：预算不足时按「当前章简介 + 卷节 > 最近 3 章摘要 > 附录补充设定 > 更早摘要」裁剪。

### 8.10 ★难点十：架构自洽（依赖方向与文件粒度）

**问题**：设计约定「Agent 逻辑不外溢到 api/services，非 Agent 业务代码也不进入 agent/」，
但同时又约定 `agent/loop/llm/`（前为 `agent/llm/`）存放 ChatModel 工厂——而 `services/llm.py`（Provider CRUD 业务服务）
必须用该工厂做「连接测试」和「降级链解析」。**这条禁令在该处不可能被满足**，
导致实现里出现 9 处 `services → agent` 反向依赖，并用 172 处函数内延迟导入规避 import 环。

**已落地的整改**（在不把 Agent 相关文件迁出 `agent/` 的前提下）：

| 动作                                                                                                                                          | 结果                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4 个纯数据访问函数（会话列表/工具日志/会话校验/项目字数）从 `loop/runner.py` 迁入 `services/agent.py`                                     | 14 个 api 模块取数路径**全部归一**（都经 services）；`api/agent.py` 只保留 `run_manager` + `sse_bus` 两个**运行入口**                                                                                                              |
| `BUILTIN_SKILLS_DIR` 路径常量下沉 `core/paths.py`                                                                                         | 消除 `services/skills.py` 的反向 import（后续包内技能目录移除，该常量一并删除）                                                                                                                                                                    |
| `BUILTIN_SUBAGENTS`（Agent 运行语义数据）**留在** `agent/subagents/builtin.py`，新增 `core/catalog.py` **函数级惰性访问器** | 消除 `services/subagents.py` 的反向 import，且 core 在模块加载期不触碰 agent → import 图仍无环                                                                                                                                                    |
| `loop/runner.py`（1420 行 / 7 类职责）拆为 6 个模块                                                                                         | runner **1420 → 375 行**，只留 run 生命周期；流程编排完整归入 `writing_steps/`（消除「一个功能劈两半」）                                                                                                                                    |
| `agent/` 各 `__init__.py` 实现外提到具名模块                                                                                              | 子包**风格统一**（`__init__` 一律纯 re-export；重组为 7 个顶层目录后延续此约定），找代码时可预期实现落点                                                                                                                                     |
| `schemas/`（424 行）与 `db/models/`（335 行）按域拆 4 文件                                                                                | 可发现性提升；`__init__` re-export 使既有 `from app.schemas import X` 写法零改动                                                                                                                                                                 |
| `services → agent` import                                                                                                                  | **9 → 6 处**（余下为 LLM/MCP/可观测基础设施 + 2 处文档化能力型例外）                                                                                                                                                                          |
| 函数内延迟导入                                                                                                                                | **161 → 86 处**（续：批量上移非环、非受控导入到模块顶层；余下 85 处是 `try:` 内的**可选/平台依赖守卫**（tiktoken、各 langchain provider SDK、winreg、langfuse 等，上移会破坏缺依赖降级）+ 1 处成环延迟导入（`builder → runner`）） |

**明确保留的现状**：`agent/loop/llm/factory.py`、`agent/more/mcp/adapter.py`、`agent/more/langfuse/` 仍在 `agent/` 内（新路径）。
彻底消环需把它们下沉到 `core/`，但那会把 Agent 基础设施迁出 `agent/`，
与「把 Agent 当成一个整体来使用」的项目定位冲突，故保留 `services → agent` 的这几处依赖并接受
函数内延迟导入作为代价。

**验证方式**（确保是纯重构、零行为变更）：用独立 git worktree 检出改动前版本，
把 SQLAlchemy metadata（16 表 × 列/类型/默认值/索引/约束/命名约定）与 OpenAPI（81 操作，重构当时）
分别 dump 成 JSON **逐字比对**，确认完全一致；39 个 schema class 做逐类正文比对；
全量测试与基线一致（纯重构、零行为变更）。

### 9.4 「把约束编码成常量 + 配回归测试」

本项目最有价值的质量手法：设计约束不写在文档里靠人工自觉，而是**编码成常量并配回归测试**。

| 约束                    | 落地方式                                                                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 权限规则顺序即语义      | `PERMISSION_RULES` 常量数组 + 顺序回归测试（断言与设计表逐行一致）                                                                                                          |
| 错误码规范              | `ErrorCode` 常量 + `CODE_TO_HTTP` / `CODE_TO_MESSAGE` **双映射表**                                                                                                |
| 路径与编码统一          | `core/paths.py` 集中解析，全部 `pathlib` + 显式 `encoding="utf-8"`                                                                                                      |
| ID 稳定、顺序单一写入口 | 起顺序由**插入**维护（`ordinal` 顺延 / 删除重编号），**无 reorder / move 接口**（测试断言路由与 OpenAPI 路径均不存在）+ `assert_no_manual_reorder()` 守卫函数 |

## 十、已知边界与可演进方向

### 10.1 有意的取舍（非缺陷）

| 取舍                                          | 理由                                                                             |
| --------------------------------------------- | -------------------------------------------------------------------------------- |
| **单用户、无鉴权**                      | 定位为本地写作工具；审计日志只读、无后台管理 UI                                  |
| **不用向量库 / Embedding**              | FTS5 二元切分对小说检索足够；零 Embedding 费用、零额外服务、零冷启动             |
| **不自研 Agent 框架**                   | deepagents 已提供主循环/沙箱/权限/子代理/技能/压缩；自研只增加维护面             |
| **写作业务函数不作为 Agent 工具**       | 收窄「permissions 不覆盖自定义工具」的越权面；Agent 只用文件工具碰内容           |
| **章不可跨卷移动、无手工重排**          | 顺序单一写入口（起为「插入」）优于双源；批量改 frontmatter 会放大写入并撞乐观锁  |
| **`services → agent` 保留 6 处依赖** | 彻底消环需把 LLM/MCP/可观测基础设施迁出 `agent/`，与「Agent 作为整体」定位冲突 |
| **敏感内容检查仅预留挂载位**            | MVP 不实现（`RecapInjectionMiddleware._check_sensitive` 是空挂载点）           |

### 10.2 外部依赖限制

- **mobi 导出**依赖本机安装 calibre（`ebook-convert`）；未装则该格式置灰并返回 `50301`
  （markdown / epub / txt 不受影响）；
- **浏览器定位**需 HTTPS 或 localhost，且用户可拒绝 → 回落 `user_settings.city`；
- **Langfuse** 三项配置全空则追踪全链路 no-op 降级为本地结构化日志；
- **FTS5** 不可用则检索永久降级 `LIKE`（返回结构不变，`data.degraded=true`）；
- **第三方 MCP** 仅支持开源免费、无需认证的服务（无认证头/Token 配置字段）。

### 10.3 可演进方向

| 方向                     | 说明                                                                                                                                                                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **基础设施下沉**   | 把 `agent/loop/llm/`（factory/params）与 `agent/more/mcp/adapter` 传输层下沉到 `core/`，可消除剩余 3 处主要反向依赖；函数内延迟导入已收敛到 86 处（85 处为 `try:` 可选依赖守卫 + 1 处成环），进一步上提需先消环。**代价**：需同步修订目录边界约定（Agent 基础设施将不再全部位于 `agent/` 内） |
| **架构契约自动化** | 引入 import-linter，把「services 不得静态 import agent（白名单例外除外）」写成 CI 契约，防止架构再度漂移（当前靠文档约定 + code review）                                                                                                                                                                      |
| **多用户 / 鉴权**  | 现为单用户；若要多用户需引入认证层、把 `project_id` 隔离升级为 `user_id + project_id`、并重新审视 WorkspaceGuard 的白名单根                                                                                                                                                                               |
| **敏感内容检查**   | `RecapInjectionMiddleware._check_sensitive` 挂载位已预留，可接入内容安全服务                                                                                                                                                                                                                                |
| **检索增强**       | 若二元切分召回不足，可加 `trigram` 作 ≥3 字查询的补充索引（★不能替代主方案），或引入向量检索作混合召回                                                                                                                                                                                                    |
| **流程提示词调优** | S1/S3 判定质量取决于提示词；判定（理由+分数）已写 Langfuse observation/score，`workflow_result_json` 留存，可基于真实数据回归调优                                                                                                                                                                           |
| **子代理并行**     | 当前子代理由 deepagents 调度（`general-purpose` 自动追加）；若有明确的并行分工需求，可在 builder 层引入显式编排                                                                                                                                                                                             |
